# 软件通用工程

将用户当前目标推进到有证据支持的完成状态。沿用目标项目的架构和工具，从已有功能中找出需要补齐的最小业务闭环。本文提供决策方法，不指定框架、目录、供应商或发布平台。

## 1. 先确定任务与当前基线

识别本轮要求是解释、诊断、审查、设计、修改还是发布。只审查时提供发现和证据；要求修改时继续实施；要求发布时核实具体目标后执行。既有授权持续有效，不要求重复确认；只有缺失选择会改变结果或需要扩大权限时才问。

先看仓库说明、适用的 `AGENTS.md`、架构约束、近期相关提交和实际运行入口。对于 Git 仓库，核实：

```text
git status --short --branch
git rev-parse HEAD
git worktree list
git diff --stat
git diff --cached --stat
```

记录本任务允许改动的模块、必须保留的行为和已存在的工作区改动。未跟踪文件也可能是用户成果，不把清空工作区当作交付步骤。多人工作或分支可能互相影响时才使用独立 worktree；不要复制敏感配置来方便隔离。

区分三类信息：当前代码事实、当前执行证据、历史记录。报告中的 PASS 只能证明对应提交和环境。文档与代码不一致时查明变更来源，不能随意选择更方便的版本；涉及冻结契约或线上数据的未决冲突先列为阻断，继续不依赖它的工作。

## 2. 把需求变成可验收的边界

为有实质行为变化的任务写一份简短任务契约，包含：

- 用户从哪个入口执行什么动作，成功时能观察到什么。
- 涉及哪些角色、模块和数据所有者；哪些能力沿用现有系统。
- 输入、输出、错误、权限、状态变化和兼容要求。
- 本轮包含与不包含的工作，以及对应的验收证据。

选择一个能从入口走到结果的业务闭环，而不是把所有页面或接口各做一半。只有改变领域归属、长期架构边界或受保护契约时，才依项目惯例补充 ADR 或设计记录。简单修复不强制长篇方案或重复审批。

不能归属的需求先查现有架构，不直接加入一个通用大模块。遇到阻断，说明阻断的是代码实施、真实集成、设备验证还是发布；不让一个设备或账号缺失阻止所有独立工作。

## 3. 先核对契约，再改实现

沿真实调用路径阅读入口、客户端适配、服务端处理和数据访问。接口存在不等于契约匹配，重点核对字段语义、分页总数、完整标识符、金额单位、空值、错误以及权限来源。

按实际改动选择以下约束：

| 改动对象 | 需要守住的行为 |
| --- | --- |
| 分层与数据归属 | 沿用现有分层；业务判断和权限放在项目规定的位置，跨模块使用公开接口。不要为一次功能绕过数据所有权。 |
| 共享能力 | 身份、媒体、审核、消息等复用已有服务；不能为演示另建旁路或让前端自行宣布成功。 |
| 状态推进 | 保留合法转换和终态；已有版本号或 CAS 机制时传递并校验期望版本，拒绝过期写入。 |
| 重试与副作用 | 区分重试同一意图和创建新意图。同一幂等请求保留标识；异步事件沿用现有 Outbox/Inbox 或等价机制，不承诺无依据的“只执行一次”。 |
| 权限和可见性 | 未知或失败的鉴权、审核、归属判断不能被当作放行；UI 隐藏不能代替服务端保护。 |
| 金额与配置 | 沿用最小货币单位整数或项目既定精确数值类型。业务可调参数走现有配置边界；历史交易按发生时快照解释，不按新费率重算。凭证不进入运营配置。 |
| 数据迁移 | 查看当前迁移登记和实际 schema；不硬编码历史“下一号”。已应用迁移按项目策略保护，新增迁移记录数据兼容与回退或前向修复办法。 |

这些是条件性检查，不要求每个项目引入领域架构、消息队列或配置中心。只在当前业务确实需要且已授权时增加机制。

## 4. 按闭环实施，保留可回退路径

优先延用现有组件、服务、错误类型和测试入口。先补齐或修正契约，再连通真实读写，最后处理交互与视觉。跨端变更跟踪每一端是否已落地，不把“后端完成”写成“功能完成”。

视觉修改也要保留真实数据、分页、导航参数、身份切换和功能开关。检查空态、加载失败、长文本、大数值、窄屏、滚动与键盘遮挡；新增控件必须有真实结果或明确的不可用状态。

修复缺陷时优先复现真实失败路径。按风险添加有意义的回归测试；低影响文字修改不堆测试，关键写入要覆盖冲突、失败和重复请求。不要用匹配源代码字串的检查代替运行行为测试。

遇到环境故障先查依赖、版本、磁盘、端口和进程。不要把资源不足误当产品错误，不自动清理用户文件或终止不属于本任务的服务。只修复本任务范围内的原因。

## 5. 按证据层级验收

开始验证前读取 [验收清单](references/acceptance-checklist.md)，按改动风险选检查，并读取所选测试入口，确认是否会写数据库、上传、发消息或触发计费。

从相关检查逐步扩大到仓库要求的检查。执行顺序和命令来自当前项目配置，不照搬其他仓库的 `npm`、`go test` 或版本要求。必要检查通过后停止重复运行，除非新改动或新问题要求复验。

每项结果注明目标、环境、执行方式和结论：`PASS`、`FAIL`、`BLOCKED`、`NOT_RUN` 或有理由的 `N/A`。分别报告：

1. 静态与自动化：类型、边界、测试、构建。
2. 本地运行：真实操作、错误路径和持久化结果。
3. 指定集成环境：真实数据库及外部服务。
4. 设备和平台：真机、多账号、平台权限与审核状态。
5. 发布后：目标版本已部署、关键业务回归及必要回滚保障。

隔离库与 mock 可用于开发测试，但不能替代用户指定的真实环境验收。运行时 schema 与迁移漂移时保留证据，不通过重建空库掩盖，也不让启动时自动迁移悄悄修改已管理表。

本地构建通过不等于已上线；公开健康端点正常也不证明本次提交已部署。缺少证据的层级保留未验证状态，不以模糊的整体 PASS 覆盖阻断项。

## 6. 交付、提交与发布

读取 [报告模板](references/report-template.md)，按任务规模输出结果。普通任务可以只用简短说明；复杂任务保留开发、验收、证据和必要的根因或残留记录，避免生成重复文档。

交付时说明做了什么、依据什么认定有效、还缺什么。引用本次实际产物与证据，明确测试数据、文件、临时服务和云对象的归属及清理情况。沿用系统的保留期或 GC，不为了报告“零残留”强删共享资源。

当本轮已授权提交或发布时，检查本任务差异，仅按文件清单暂存并复核暂存内容，然后提交。保留其他改动，不使用全量暂存来凑“干净工作区”。只在项目策略或明确请求要求时打标签；记录实际提交号，不把暂存当提交。

向 GitHub 推送前核对目标仓库、分支和待推送提交范围，避免把其他未发布工作一并推出。使用普通推送；非快进时检查差异并按既定协作方式处理，不自动强推或重写共享历史。推送后核实远端提交；仅在请求包含或工作流要求时创建 PR。

发布到生产、上传平台、提交审核、合并及向他人发送消息，各自需要在授权范围内。已有明确授权就继续；缺失时先完成可审核的产物和检查，再说明具体缺少的决定。

## 维护本方法

修改此 skill 后可使用 [行为场景](evals/evals.json) 检查是否仍能守住任务边界与证据层级。场景与预期不是运行结果；只有实际执行才记录为行为验证通过。根据真实使用中暴露的问题小幅改进，不把每次事故扩展成所有项目的强制流程。
