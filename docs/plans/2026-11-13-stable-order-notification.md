# 稳定订单通知方案

> 2026-11-13 决策：当前“湛科生活圈”公众号是个人主体、未认证的普通公众号，不满足服务号 OAuth 与模板消息条件。项目不再把服务号作为上线依赖；正式方案采用小程序内通知、可累积订阅额度和企业微信群。本文关于服务号的内容仅作为未来可选方案保留。

本方案区分“稳定必达的站内通知”和受微信授权额度限制的站外提醒。任何方案都不能绕过用户授权或微信平台规则。

## 现状

- 配送单状态变化已经会生成商家和当前骑手的站内通知。
- 新单进入待接单池后，会向当前在岗且未满载的骑手生成候选通知。
- 微信小程序订阅消息采用一次性额度：用户每授权一次，只增加 1 条可发送额度；系统支持多次授权和多额度累积。
- 生产当前 `NOTIFICATION_AUDIENCE=test`，只允许 `NOTIFICATION_TEST_USER_IDS` 中的账号发送微信消息，因此实际放行账号只有 1 个。
- 全量模式代码已支持 `NOTIFICATION_AUDIENCE=all`：所有状态正常、开启订单通知、在免打扰规则内且当前有未使用额度的商家/骑手均可进入发送队列。

## 推荐分级方案

### 1. 立即启用：站内必达 + 全量微信订阅额度

- 站内通知始终生成，不依赖微信授权额度。
- 生产切换为：

```text
NOTIFICATION_AUDIENCE=all
NOTIFICATION_TEST_USER_IDS=
```

- 用户每次点击“补充 1 次”并接受微信授权后，数据库增加一条一次性额度。
- 每笔可通知订单状态消耗一条额度；余额、结果和失败状态均由服务端记录。
- 该方案适合中低订单量，不能承诺用户拒绝授权后仍收到无限微信提醒。

### 2. 稳定多单提醒：绑定微信服务号

- 将小程序与服务号绑定在同一微信开放平台账号下，使用 UnionID 关联用户。
- 用户关注服务号并完成通知授权后，由后端服务号模板消息按订单发送；是否可长期、按次发送以公众号类目、模板审核和平台当期规则为准。
- 建议增加独立绑定表，保存 UnionID、服务号 OpenID、关注状态、模板授权和用户偏好的通道。
- 订单队列优先使用服务号通道，小程序订阅消息作为未关注或发送失败时的兜底。
- 该方案最适合“商家/骑手每天多单、需要持续提醒”的场景。

### 3. 运营侧稳定提醒：企业微信群或应用消息

- 商家可按门店创建企业微信群机器人，骑手按配送组创建群机器人。
- 新单、超时、取消和异常状态同时发到群内，适合多人同时值守。
- 项目已有骑手企业微信发送器的扩展基础，可继续补齐商家门店维度的绑定和路由。
- 群提醒不会替代个人微信提醒，需与站内通知并行。

### 4. 实时站内提醒

- 当前通知中心通过轮询和 IM 事件刷新。
- 后续可新增服务端到用户的 IM 自定义系统消息或 WebSocket 通道，在页面打开时即时弹层、振动和更新角标。
- 这不消耗微信订阅额度，但用户完全退出小程序后不能代替微信站外推送。

## 实施顺序

1. 将生产通知受众从单账号测试切到 `all`，并保留额度不足时不发送、不伪造成功。
2. 在商家发单页、骑手开工页增加“订单提醒额度”入口和一次补充授权，减少用户必须进入设置页的成本。
3. 接入微信服务号 UnionID 绑定、关注状态和模板消息，作为稳定多单主通道。
4. 为商家门店和骑手班组接入企业微信群通知，覆盖多人值班场景。
5. 增加 7/30 天发送统计：授权额度、剩余额度、微信受理、拒绝、阻塞和点击回流，持续调整即时与合并提醒策略。

## 关键限制

- 不能通过一个普通一次性订阅模板获得永久无限推送。
- 不能自动代替用户在后台连续点击多次授权。
- 服务号模板消息需要真实公众号资质、类目、模板和用户关注/授权。
- 站内通知可以作为稳定业务底账，站外通道必须允许失败、重试和人工排查。
