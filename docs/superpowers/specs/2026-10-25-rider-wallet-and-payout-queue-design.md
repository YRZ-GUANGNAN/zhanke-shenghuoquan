# 骑手钱包与平台待打款队列设计

日期：2026-10-25。基线：当前分支 `codex/native-theme-motion-20261025`，支付资金核验提交 `5d12db4`。

状态：2026-10-25 用户已确认钱包/UI、“平台内部待打款队列，微信通道后接”，以及现在实施余额占用、取消释放和并发互斥。施工单自审发现上一稿将真实队列与只读收益报表混淆；本次补正将二者分开并固定真实资金边界。本设计不启用真实转账、不执行生产迁移、不把线下结款登记包装为微信到账。

## 1. 目标与边界

本批完成两个正式入口：

1. 商家钱包：沿用现有蓝色视觉，展示服务端余额、资金状态、待核实提示、分页账单，并修复支付能力检查、刷新失败和充值原单恢复语义。
2. 骑手收入：注册正式 `rider-wallet` 页面，从骑手“我的”进入；展示本人账面未结款余额、今日完成单量/收入、排队占用、来源待核验、已登记线下结款和分页收入流水。骑手端只读，不提供充值、提现或后台线下结款按钮。账面余额不是可提现余额，不能标成微信可到账金额。

3. 平台内部待打款队列：新增独立、持久化的排队记录和收益占用，而不是把 `RiderEarningRecord` 列表更名为队列。入队方式为内部任务自动扫描已完成、未结款且来源已核验的收益；本批不新增骑手提现申请，不自动付款。后台可查询排队事实、占用和阻断原因。微信商家转账适配器、收款授权、回调验签、外发 worker 和真实打款属于下一阶段。

现场证据：`settleDeliveredOrderTx` 当前生成 `RiderEarningPending`；没有正常写入 `settled` 的生产路径。`pending` 和 `settled` 都须参加未结款候选检查，二者均不能单凭状态判定可出款。`paid_offline` 必须排除，不创建第二笔待付款。

## 2. 数据与接口

### 2.1 骑手只读接口

在 `backend/internal/module/admin/deliveryrider` 的正式骑手路由下新增 `GET /delivery/rider/wallet`，继续使用登录和骑手身份守卫。服务端从会话取得 `riderUserID`，不得接受客户端传入用户 ID。

返回钱包汇总，分页收益与流水走独立读取接口，避免两个列表共用页码：

- `wallet`: `walletPublicId`、`availableBalanceCents`（账面未结款）、`reservedCents`（排队占用）、`unverifiedCents`（来源待核验）、`updatedAt`；
- `today`: 复用已有上海时区“已完成且产生骑手收入记录”的今日统计；
- `GET /delivery/rider/wallet/earnings`: 分页收益记录，包含订单公开编号、金额、`pending/settled/paid_offline` 状态、创建时间和线下结算时间；
- `GET /delivery/rider/wallet/ledger`: 分页骑手流水，包含方向、类型、金额、余额快照、引用编号和创建时间；
- `GET /delivery/rider/wallet/payout-queue`: 本人排队记录，只包含公开 ID、金额、排队状态、可对用户展示的阻断原因和时间。

读取必须是只读查询，不调用会创建钱包的 `RiderWallet()` 命令方法；数据库成功确认既没有钱包也没有收益时，返回 `walletState=not_created`、零余额和空列表。缺表、数据库失败或钱包缺失但已有收益是不可用/一致性异常，不能伪装为零余额。队列表未迁移时排队金额返回不可用，不能伪装成已查询且为零。

各返回对象使用显式 DTO 白名单，不直接序列化 GORM 模型。禁止向骑手返回操作者 ID、后台备注、幂等键、租约、付款人 openid、微信交易原文和资金来源内部证据。查询只能读取当前会话本人；客户端传入其他用户 ID 不得改变作用域。

### 2.2 商家钱包

保留既有 `/delivery/merchant/wallet`、`/ledger` 和充值接口。正式页面统一使用支付核验字段：`providerStatus`、`nextVerifyAt`、`verifyAttemptCount`。充值请求在网络未知、取消支付或页面卸载后保留原 `clientRequestId/paymentPublicId`，刷新时查询原单，不创建第二笔订单。客户端只保存账号隔离的恢复标识和金额，不保存签名或微信支付密钥；同账号恢复可查原单，换账号不能回流旧数据。没有 payment ID 时只允许用原幂等号恢复同一充值业务，不生成新号重试；取消页面不等于后台已关单。

### 2.3 平台待打款队列

首期按一笔收益整笔入队，不开放任意金额、部分占用或部分付款。新增队列表与占用记录，队列公开 ID、`earningPublicId`、订单公开 ID、骑手 ID、整数分金额、资金来源核验快照版本、`rowVersion` 和创建/更新时间持久化。收益公开 ID 有唯一约束，重复扫描/重试返回原记录；同一收益身份或金额不一致返回冲突，不能覆盖快照。迁移只创建结构，不把历史收益、钱包金额或未知来源静默回填为已核验、已占用或已排队。

账面口径固定如下：`availableBalanceCents` 继续表示现有账本中的未结款余额，创建或取消队列都不修改该字段；`reservedCents` 是所有有效 `queued` 占用之和；可继续结算金额为 `availableBalanceCents - reservedCents`，不得小于零。只有 `queued` 产生有效占用，`blocked` 不占用，`cancelled` 已释放。队列创建不写 `RiderLedgerPayout`，取消也不增加账面余额；真正出账只能由未来微信通道或现有线下结款流程在独立事务中完成。

本批状态严格限定：

| 状态 | 含义 | 资金行为 |
| --- | --- | --- |
| `blocked` | 来源未核实、旧数据缺链或一致性异常 | 不产生占用，不标记失败付款 |
| `queued` | 来源核验通过，已占用对应收益，等待通道 | 保持账面余额，不写出账流水 |
| `cancelled` | 管理员取消尚未外发的内部排队 | 原子释放占用一次，不增加账面余额 |

本批没有 `processing/succeeded/unknown` 写入口，因为没有外部转账尝试；未来接通道须新增独立尝试模型及相应迁移。后台“批准”、HTTP 成功、扫描成功和取消队列都不能使收益变成已打款。

入队任务仅访问本地数据库，不触发微信 API。创建/扫描生产开关默认关闭，本批只提交本地代码；没有队列表/占用表或配置错误时拒绝启动入队任务，不隐式执行迁移。新旧未结款收益均通过稳定分页扫描，只有来源核验通过才建立占用。重复扫描的终态 `cancelled` 不自动重新入队；重新入队策略不在本批。

### 2.4 来源核验与账本互斥

- 微信直付来源必须核对订单、商家、费用快照、支付用途、币种、金额、支付终态和可信交易编号的对应关系；退款中/已退款不入队。
- 钱包付费沿收益 → 订单 → `FeeSettlement` → `FundingAllocation` → `FundingLot` → 原充值记录核验。首期仅整笔配送费分配全部为真实微信已核验来源、分配金额守恒且没有释放时允许占用对应骑手收益；混合 mock/历史未知来源整笔阻断，不猜测资金分摊。
- 对同一骑手，排队占用不得超过其账面未结款余额；对同一收益，占用与既有结款不能重复。使用数据库事务、唯一约束和统一锁序，不能依赖前端防重。
- 入队、取消、现有线下登记统一锁序：先定位骑手但不持锁，再锁钱包、目标收益/来源及队列/占用；重新核验版本后写入。遇到差异整体回滚，不创建残留占用。
- `pay-offline` 保持现有管理员权限，不暴露给骑手。收益存在有效占用时返回冲突，必须先通过管理员取消内部队列释放占用，再使用原线下登记流程；不能在该请求中悄悄取消队列后付款。
- `POST /admin/delivery/rider-payout-queue/:id/cancel` 仅管理员可调用，要求 `expectedRowVersion`、幂等键、原因，记录操作者和审计事件。不提供直接标记已打款或修改金额的接口。
- 每个资金写路径必须有未登录、普通用户、错误身份、他人资源、过期版本、重复请求和并发竞争的拒绝/幂等测试；新增权限不能扩大现有线下登记的授权范围。

## 3. UI 设计

- 钱包主卡保留当前蓝色渐变和原返回按钮；不换主题、不增加玻璃材质或新导航。
- 商家顺序：余额主卡 → 资金状态/待核实说明 → 账单流水。刷新为现有触控规范，失败保留已知余额和流水，提供原地重试。
- 骑手顺序：账面未结款主卡 → 今日单量/今日收入双指标 → 排队占用/来源待核验 → 收入、流水和排队记录。页面明确“等待接入打款通道”；`paid_offline` 仅显示“已登记线下结款”，不写“微信到账”。预览中的“可用结算余额”改为“账面未结款余额”，示例数字须满足相应资金关系。
- 骑手页面不出现充值、提现、自动打款或改变结算状态的操作。内部入队为系统行为、不是用户申请提现；自动付款仍未开通。后台可查队列和审计，仅可取消未外发排队，不显示假“打款成功”。
- 空态为“说明 + 刷新/返回”，错误为“保留已有数据 + 重试”，禁止把能力检查中/网络故障显示为“未开通”。
- 继续遵守当前页面的身份守卫、账号/token/卸载隔离、手势返回与 44px 触控目标。

## 4. 错误与资金安全

- 读取失败不能清空上一份已确认余额或流水；各分区独立显示错误。
- 骑手收益统计、可用余额、待打款金额分开显示，不能用今日收入替代可提现余额。
- `paid_offline` 只表示后台有线下付款登记；它不是微信支付结果，也不触发骑手端“到账”提示。
- 充值/支付未知或超时只允许查原单或按原幂等号恢复，不能据此入可打款队列。内部排队请求超时先查原记录或重放同一幂等操作，不创建第二份占用。
- 所有新的内部队列写操作使用服务端幂等键和 CAS；前端防重只作为体验层保护。
