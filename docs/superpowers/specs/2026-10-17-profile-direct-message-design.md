# 个人主页发起私信

用户已要求直接实施，本轮沿用隔离分支 `codex/public-profile-20261017`，不修改原项目，不部署、不上传、不发送真实测试消息。

## 方案

在他人主页的关注旁增加“私信”。点击进入现有聊天页，以 `userId` 为入口；聊天页通过鉴权接口取得双方的真实会话和公开头像昵称。自己的主页不显示此按钮，私信总开关关闭时入口隐藏。

选择扩展现有 IM 关系，而不是虚构商品关系或另建消息系统。新增 `PUT /im/users/:userId/conversation`，用户对按 ID 排序，以 `reference_type=user, reference_id=0` 唯一存储，复用现有唯一索引，无数据库迁移。反向进入、重复点击返回同一个关系。继续使用 Tencent C2C；同一对用户已有商品聊天的历史自然属于同一个 C2C，不新建群、不保存消息正文。

用户会话返回 `referenceType=user`、`productId=0`；原商品会话返回 `referenceType=product`，前端兼容旧接口未返回类型的商品会话。用户私信不请求商品、不展示商品栏或买卖提示，头像与主页入口沿用现有组件。消息列表按 C2C 对方去重并优先采用用户会话，避免同一人出现两行相同聊天。

## 权限与失败处理

用户私信由 `messages` 控制，商品咨询另需 `secondhand_chat`。服务端在授权关系之后判断类型，列表在数据库分页前过滤关闭的商品咨询；客户端不能通过改 URL 解锁商品会话。新建和重进用户聊天检查双方账号状态与双向拉黑；实际客户端发送前重新读取授权关系，失败不调用 SDK、不清草稿。不改变已有 Tencent 服务端回调规则，不声称此检查可以替代 Tencent 的服务端风控。

保留已有认证、账号切换取消、卸载取消、输入互斥、失败草稿。拒绝自己、无效 ID、不存在/停用账号、拉黑及未登录请求，错误文案不暴露数据库信息。
