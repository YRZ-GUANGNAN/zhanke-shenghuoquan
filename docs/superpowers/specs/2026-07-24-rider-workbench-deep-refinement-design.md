# 骑手工作台深度精修设计

## 背景

骑手工作台已经恢复旧版的完整业务结构，并继续使用真实骑手身份、真实订单和真实配送状态。当前主要问题集中在视觉层级和移动端排版：

- 蓝色头部信息密度过高，头像、姓名、认证状态、任务数据和刷新入口互相争夺注意力。
- 微信官方胶囊虽然已预留安全区，但页面内容与胶囊所在区域的视觉关系仍显拥挤。
- 刷新入口像独立悬浮白块，与头部其他信息不属于同一套组件语言。
- 三段订单状态导航层级偏弱，数量、标签和选中反馈较碎。
- 列表说明和刷新入口重复，空状态卡片比例失衡，页面存在大量无意义留白。
- 部分字符被当作图标使用，图标的线宽、尺寸和视觉重心不一致。

## 目标

在保留旧版骑手工作台业务骨架的前提下进行明显的深度精修，使页面更清晰、紧凑、可信，并符合移动端配送工作台的使用习惯。

本次需要做到：

- 保留蓝色骑手头部、身份信息、当前任务统计、三段状态导航和订单列表。
- 微信官方胶囊继续独占安全行，任何自定义按钮和文字不得进入胶囊点击区域。
- 重建头部内部层级，降低视觉噪声，不把页面改成另一套产品。
- 统一图标、字号、间距、圆角、边框和状态反馈。
- 区分加载、空列表、失败和有订单四类状态。
- 保持真实身份审核、真实订单、真实联系方式、真实凭证上传和真实状态流转。

## 设计方向

采用已确认的 C 方案“深度精修”：

- 保留现有功能分区和主要顺序，但允许明显调整分区比例、内部排版和组件外观。
- 蓝色头部继续作为骑手端识别区，但减少廉价高亮渐变、装饰圆和厚重阴影。
- 页面主体以订单阶段和当前任务为核心，不以装饰性数据面板为核心。
- 使用清晰的线性图标，不使用“骑”“C”等文字字符冒充图标。
- 整体呈现应专业、轻量、可快速扫描，避免像缩小后的桌面后台。

## 页面结构

### 1. 胶囊安全行

- `CapsuleSystemRow` 保持在页面最上方。
- 胶囊所在行只承担系统安全空间，不放身份切换、刷新、标题或其他可点击元素。
- 安全行高度继续从微信胶囊尺寸动态计算，兼容模拟器和真机差异。

### 2. 蓝色身份区

- 蓝色头部保留，但整体高度相对当前版本适度降低。
- 身份区排列为一条稳定的信息轴：
  - 左侧为真实姓名首字头像。
  - 中部为真实姓名、骑手标识和认证/接单状态。
  - 右侧为“切换身份”入口。
- 姓名作为一级信息；骑手标识与状态作为二级信息，不再全部压缩为同等大小的小字。
- 身份切换入口采用轻量描边按钮，不与胶囊重叠，不伪装成系统控件。

### 3. 当前任务区

- 当前配送任务数量仍位于蓝色头部内，但改为紧凑横向信息区。
- 主数字显示正在取货和正在配送的真实任务总数。
- 可抢订单数和已完成订单数作为次级统计，弱化显示。
- 刷新入口与任务数据处于同一基线，使用标准刷新图标和“刷新”文字。
- 删除独立白色方块式刷新按钮。
- 刷新时只旋转图标并显示轻量状态，不清空现有数据，不让页面闪白。

### 4. 订单状态导航

- 保留“待抢单”“待取货”“待送达”三段状态。
- 三段等宽排列，数量作为紧随标签的紧凑徽标。
- 选中态使用清晰的主色文字、浅色背景或底部指示条；未选中态降低对比度。
- 切换状态不改变导航本身高度，避免页面抖动。
- 每个状态分别保留自己的滚动位置；若当前技术结构无法可靠保存，至少不得在切换时触发整页重载。

### 5. 列表与空状态

- 列表直接承接状态导航，移除重复的“当前共 N 单”和第二个刷新入口。
- 有订单时，订单卡片优先展示：
  - 订单编号和配送阶段。
  - 真实配送费。
  - 取货点与送达点。
  - 当前阶段可用的主要操作。
- 距离只在真实接口提供可靠数据时显示；不得计算或填充模拟距离。
- 备注、隐私提示、完整地址标签和次要操作使用次级层级。
- 空状态不再使用孤立的大白框：
  - 使用统一的配送路线 SVG 图标。
  - 提供明确标题和对应阶段说明。
  - 整体高度随内容收敛，避免制造大面积空白。

## 视觉规则

### 色彩

- 保留骑手端蓝色品牌识别。
- 头部使用稳定的深浅蓝层次，减少装饰圆和高亮泛光。
- 页面背景使用偏冷的浅灰蓝，卡片使用白色或极浅蓝灰。
- 橙色只用于送达点、费用或需要注意的信息，不作为大面积装饰色。
- 错误、危险和禁用状态分别使用已有设计令牌，不新增随意颜色。

### 字体层级

- 真实姓名、当前任务主数字和订单主要操作为高优先级。
- 状态说明、统计标签和隐私说明为低优先级。
- 避免同一区域同时出现多个相近但不一致的小字号。
- 数字与单位基线对齐，中文正文保持可读行高。

### 图标

- 新增骑手页专用 SVG 图标，至少包括：
  - 刷新。
  - 配送路线空状态。
  - 消息。
  - 电话。
  - 取货点与送达点标记（若现有 CSS 标记不能保持一致时）。
- 所有图标使用统一 `viewBox`、描边粗细、圆角端点和视觉尺寸。
- 不依赖 Emoji、字体图标或网络图标库。
- 真机缩放后应保持边缘清晰、视觉居中。

### 卡片与间距

- 订单卡片使用细边框和轻阴影，减少悬浮感。
- 统一页面左右边距、卡片内边距和组件间距。
- 主要按钮在不同订单阶段保持一致位置、尺寸和圆角。
- 底部内容必须包含 `env(safe-area-inset-bottom)` 安全间距。

## 交互与状态

### 刷新

- 刷新期间保留当前订单内容。
- 刷新图标显示旋转状态，避免重复点击。
- 刷新成功后原位更新数量和订单。
- 刷新失败时保留旧数据，并在内容区显示可点击重试提示。

### 加载

- 首次进入且无缓存数据时显示专用加载状态。
- 已有数据的后台刷新不切换到整页加载占位。
- 加载状态不得使用字符“骑”作为图标。

### 空列表

- 三个状态分别显示对应文案：
  - 待抢单：当前暂无可抢配送单。
  - 待取货：抢单成功后，订单会进入待取货列表。
  - 待送达：完成取货后，订单会进入待送达列表。
- 空状态不得伪造订单、距离、收入或余额。

### 错误

- 网络或接口失败与空列表必须明确区分。
- 有旧数据时错误提示不得覆盖旧数据。
- 无数据且加载失败时提供明确重试入口。

### 订单操作

- 主操作根据真实订单状态显示：
  - 立即抢单。
  - 前往取货。
  - 确认取货。
  - 开始配送。
  - 确认送达。
- 消息、电话和释放订单继续使用现有真实能力。
- 释放订单等危险操作继续要求二次确认。
- 取货和送达凭证继续走现有上传与审核流程。

## 数据与安全边界

以下行为保持不变：

- `useIdentityGuard('rider')` 继续控制骑手身份访问。
- `getDeliveryRiderMe()` 继续提供真实骑手资料和工作状态。
- `listClaimableDeliveryOrders()` 继续提供真实可抢订单。
- `listAssignedDeliveryOrders()` 继续提供真实已分配订单。
- 抢单、释放、前往取货、确认取货、开始配送和确认送达继续使用现有服务。
- 联系电话、会话和凭证上传继续受现有订单阶段和后端权限控制。
- 身份未通过审核的用户不得进入骑手工作台。

本次不新增模拟订单、虚假余额、虚拟用户号、模拟距离或本地配送收入。

- `scripts/check-miniapp-capsule-layout.cjs`

- 骑手身份审核规则。
- 订单状态机。
- 支付功能开关。
- 商家端和学生端页面。

## 验收标准

### 视觉验收

- 微信胶囊独占安全行，任何页面元素不与其重叠。
- 蓝色头部仍能明显识别为原有骑手工作台，但层级更清晰、整体更紧凑。
- 头像、姓名、骑手标识、认证状态和切换入口对齐稳定。
- 刷新入口不再是独立白色方块，并具有清晰的加载反馈。
- 三段状态导航选中态明确，文字和数量不拥挤。
- 页面不再出现“骑”“C”等字符图标。
- 空状态比例合理，不产生大面积无意义空白。
- iPhone 15 Pro 模拟器和至少一种较窄屏幕下无截断、溢出或错位。

### 功能验收

- 未审核用户仍无法进入骑手工作台。
- 已审核骑手可以正常切换身份、刷新和切换三个订单状态。
- 可抢订单、待取货订单和待送达订单均来自真实接口。
- 抢单、取货、配送、送达、释放、消息和电话入口行为不变。
- 接口失败、加载中和空列表显示不同状态。
- 支付未开通不影响骑手订单工作台的读取和操作边界。

### 自动验证

- 小程序类型检查通过。
- 骑手业务闭环静态检查通过。
- 胶囊布局静态检查通过。
- 身份申请与身份门禁相关检查通过。
- 新增图标和视觉边界静态检查通过。
- 微信小程序生产构建通过。

### 手动验证

- 微信开发者工具中依次检查待抢单、待取货、待送达三个状态。
- 检查首次加载、后台刷新、空列表和接口失败状态。
- 检查胶囊、身份切换和刷新入口的点击区域。
- 使用真实审核通过的骑手账号验证真实订单操作。
- 真机验证凭证上传、电话和会话入口。

## 非目标

- 不重写骑手配送业务。
- 不新增钱包、提现或配送收入结算页面。
- 不新增地图、轨迹或距离计算服务。
- 不修改底部学生端导航。
- 不扩大到商家端、学生端或管理后台的视觉改造。
- 不处理与本规格无关的现有未提交文件。
