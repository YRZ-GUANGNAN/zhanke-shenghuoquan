# 二手商品留言、卖家操作与自动审核设计

> 日期：2026-07-29  
> 状态：方案已确认，待实施计划

## 1. 背景

当前正式二手商品详情页承担商品展示、收藏和联系卖家的买家流程，但缺少三项完整闭环：

1. 商品卖家无法在当前正式详情页直接把商品标记为预订或售出。
2. 商品页没有公开留言与回复，买家只能发起私信。
3. 帖子、商品及新增留言虽然进入统一审核任务，但仍需要人工逐条决定，不能按微信内容安全结果自动完成明确结果的审核。

本设计在现有二手交易、统一审核和站内通知能力上扩展，不替换现有私信、商品发布、收藏、搜索或后台人工审核。

## 2. 目标

1. 商品卖家在正式商品详情页管理商品状态；普通买家仍使用收藏和联系卖家。
2. 商品详情页支持公开留言与一级回复，卖家回复显示“卖家”标识。
3. 帖子、商品、商品留言和回复采用“自动审核优先、可疑内容转人工”的混合审核。
4. 审核通过后产生幂等站内通知：新留言通知卖家，新回复通知被回复用户。
5. 收藏按钮改为星形，但保留现有收藏接口、计数和防重复语义。
6. 保持未审核内容不可公开，并保留管理员人工改判和审计能力。

## 3. 非目标

- 不新增微信订阅消息。
- 不新增多级楼中楼、私密留言、匿名留言或留言图片。
- 不替换腾讯云 IM，也不把公开留言写入 IM。
- 不改变商品发布、搜索索引、媒体上传和卖家联系入口的现有契约。
- 不自动审核商家、骑手等身份申请；身份材料仍由人工审核。
- 不在本阶段配置骑手企业微信群 Webhook。

## 4. 总体方案

采用交易域内的独立商品留言模型，避免把商品映射成帖子，也避免让商品生命周期与社区评论模型耦合。

模块边界如下：

- `trade`：商品状态、收藏、商品留言、一级回复、公开读取和权限校验。
- `review`：审核任务、自动决定规则、人工兜底、审计记录。
- `community notifications`：复用现有站内通知读取与已读能力，扩展商品留言通知目标。
- MiniApp 商品详情页：按当前登录用户展示买家或卖家操作，并渲染留言区。
- Admin：继续显示待人工处理的任务，并允许管理员改判自动结果。

## 5. 数据模型

### 5.1 商品留言

新增 `product_comments` 表，至少包含：

- `id`
- `product_id`
- `user_id`
- `parent_comment_id`：顶层留言为 `0`；回复时指向一条顶层留言
- `reply_to_user_id`：顶层留言为 `0`；回复时记录被回复用户
- `content`
- `review_status`
- `client_request_id`
- `request_hash`
- `created_at`
- `updated_at`
- `deleted_at`

约束与索引：

- `parent_comment_id` 只能为 `0` 或同一商品下的顶层留言 ID。
- 禁止回复一条回复形成第二级嵌套；界面中的“回复回复”仍保存到相同顶层留言，并通过 `reply_to_user_id` 表达对象。
- `(user_id, client_request_id)` 唯一，用于幂等提交。
- 按 `(product_id, review_status, created_at, id)` 建立公开列表索引。
- 按 `(parent_comment_id, review_status, created_at, id)` 建立回复列表索引。

首期留言仅支持文字，不引入新的媒体引用关系。

### 5.2 站内通知

扩展现有 `notifications` 表，使其可定位商品与商品留言：

- 新增 `product_id`
- 新增 `product_comment_id`
- 新增通知类型 `product_commented` 与 `product_comment_replied`

唯一事件键应包含接收者、行为人、通知类型、商品和商品留言坐标，保证审核重放不会产生重复通知。本人对本人产生的行为不创建通知。

## 6. 商品状态与权限

正式商品详情页根据服务端返回的真实 `sellerId` 与当前 session 用户判断视角：

- 买家视角：显示星形收藏和“联系卖家”。
- 卖家视角：不显示“联系卖家”，显示“标记预订”“标记售出”和按状态允许的“重新上架”。

所有状态修改由服务端重新读取商品并校验所有权，前端判断仅用于展示。允许的状态转换为：

```text
selling -> reserved
selling -> sold
reserved -> selling
reserved -> sold
sold -> selling
```

商品进入 `sold`、被下架或删除后：

- 保留已公开留言供历史查看。
- 禁止新增留言和回复。
- 禁止新收藏和新建联系关系。

## 7. 留言与回复接口

在鉴权的交易路由下增加：

```text
GET  /api/v1/trade/products/:id/comments?page=&pageSize=
POST /api/v1/trade/products/:id/comments
POST /api/v1/trade/products/:id/comments/:commentId/replies
```

提交请求包含：

```json
{
  "content": "留言正文",
  "clientRequestId": "ULID"
}
```

回复接口另包含服务端从目标留言推导的顶层留言和被回复用户，不接受客户端伪造 `productId`、`parentCommentId`、`replyToUserId` 或卖家标识。

公开列表只返回 `approved` 内容。提交者读取同一商品时，可额外看到自己的 `submitted`、`reviewing`、`rejected` 内容及安全的状态说明。回复按顶层留言分组，仅展示一级视觉层级。

## 8. 混合自动审核

自动审核覆盖：

- 社区帖子
- 二手商品创建与修改
- 商品留言
- 商品回复

文字继续使用服务端认证用户的真实 OpenID 调用微信文本内容安全检查。未来若留言支持媒体，媒体仍走现有异步媒体审核；本期商品留言只有文字。

自动决定规则：

| 结果 | 审核动作 | 对外可见性 |
| --- | --- | --- |
| 微信明确安全 | 自动批准 | 审批事务完成后公开 |
| 微信明确违规 | 自动拒绝 | 仅提交者可见 |
| 结果可疑或需要复核 | 转人工 | 不公开 |
| 未配置、超时、网络失败、响应异常 | 重试后转人工 | 不公开 |

自动决定必须复用统一审核服务的决定入口，不能直接修改业务表状态，从而保留审核日志、业务副作用和幂等语义。管理员可以在后台查看自动决定来源并进行人工改判。

自动批准商品留言或回复时，在同一业务副作用链路中：

1. 将留言状态改为 `approved`。
2. 创建唯一站内通知。
3. 更新商品的公开留言计数（若页面展示该计数）。

审核重放不得重复增加计数或创建通知。

## 9. 页面交互

### 9.1 收藏

- 未收藏：灰色空心星 `☆`
- 已收藏：金色实心星 `★`
- 点击时提供轻微缩放反馈。
- 保留现有收藏接口、数量和重复点击保护。

### 9.2 留言区

- 商品正文下方新增“留言”区域。
- 默认按最近更新时间展示顶层留言，回复在所属留言下按时间正序显示。
- 用户可以点击留言或回复进入回复状态，输入区显示“回复某某”。
- 卖家的所有已通过回复显示“卖家”标识，该标识由服务端根据商品所有者计算。
- 新提交内容立即显示给提交者并标记“审核中”。
- 被拒绝内容只对提交者显示简短原因，并允许编辑后使用新的幂等标识重新提交。
- 可疑或审核异常内容显示“等待人工审核”。

### 9.3 站内通知

- 顶层留言通过：通知商品卖家。
- 回复通过：通知被回复用户。
- 点击通知进入商品详情，并携带目标留言坐标；页面加载后滚动或高亮对应留言。
- 通知对象已删除或商品不可访问时，显示统一不可用提示，不泄露资源存在性。

## 10. 错误处理与安全

- 未登录提交返回 `401`。
- 商品、留言不存在或无权访问统一返回 `404`，避免资源枚举。
- 商品已售出、下架或删除时提交留言返回冲突错误，前端刷新最新状态。
- 内容为空、超长或 `clientRequestId` 非法返回 `400`。
- 相同幂等键与相同请求体返回第一次结果；相同键不同正文返回冲突错误。
- 对同一用户增加短窗口频率限制，并拦截同一商品下短时间连续提交的完全相同正文。
- 自动审核失败采用失败关闭：保留待审核，不自动公开。
- 日志和 API 响应不得包含 OpenID、access token、审核原始敏感响应或企业微信 Webhook。

## 11. 测试策略

### 11.1 后端

- 商品状态转换及卖家权限。
- 买家、卖家和第三方的留言与回复权限。
- 一级回复约束、跨商品回复拒绝和被回复用户推导。
- 幂等重放、幂等冲突、重复正文和频率限制。
- 自动安全、自动拒绝、转人工、超时和重试上限。
- 自动决定重放不重复增加计数或创建通知。
- 公开读取不泄露他人的待审核与拒绝内容。
- 通知接收者、卖家标识和目标留言坐标正确。

### 11.2 MiniApp

- 买家与卖家操作区互斥。
- 商品状态切换后页面立即刷新。
- 空心星和金色实心星与真实收藏状态一致。
- 留言 loading、empty、ready、error、审核中、人工审核和拒绝状态。
- 一级回复布局、卖家标识和通知跳转定位。
- iOS 与 Android 的胶囊避让、滚动、底部安全区和输入法布局。

### 11.3 验收边界

自动化验收通过后，仍需两台真机使用两个真实账号完成：

1. 买家收藏、留言并联系卖家。
2. 卖家收到站内通知、回复并修改商品状态。
3. 买家收到回复通知并回到对应留言。
4. 分别验证自动通过、自动拒绝和转人工三种审核结果。
5. 商品售出后确认历史留言可读、新留言与新联系被禁止。

自动化测试、构建成功或单机预览不能替代双账号真机验收。

## 12. 实施边界

实施计划只应修改与以下范围直接相关的文件：

- `backend/internal/module/trade/**`
- `backend/internal/module/admin/review/**`
- `backend/internal/module/community/**` 中站内通知的最小扩展
- 新增数据库迁移及其回滚
- `backend/cmd/server/main.go` 的必要装配
- `apps/miniapp/src/pages/secondhand-detail/**`
- `apps/miniapp/src/pages/notifications/**`
- 相关 MiniApp 服务、类型和聚焦检查脚本

不得顺带重构外卖、配送、支付、腾讯云 IM、搜索、身份审核或其他页面，也不得覆盖工作区内已有的未提交改动。

## 13. 完成标准

- 卖家可以在正式商品详情页完成预订、售出和重新上架。
- 买家与卖家可以完成公开留言和一级回复，且卖家标识可信。
- 帖子、商品、留言和回复按混合规则自动决定或转人工。
- 未批准内容对其他用户不可见，审核失败不会绕过审核。
- 站内通知准确、可定位且不会因重放重复。
- 收藏星形状态与真实收藏状态一致。
- 聚焦后端测试、MiniApp typecheck、正式构建和边界检查通过。
- 两台真机双账号完整流程验收通过后，才标记为业务完成。
