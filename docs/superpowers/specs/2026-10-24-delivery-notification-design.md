# 配送订单与资金通知闭环设计

日期：2026-10-24。基线：`main` / `ded4c0455ae07a32991dc0f55f67cb67e3ebaef8`。

状态：依据用户要求补齐通知的设计，待书面审阅；公众号权限、绑定及实际投递尚未验证。

## 1. 范围与前提

在不重做 UI、不改现有角色权限的前提下，让商家、骑手收到真实订单和资金变化通知。站内记录为基础，公众号为外部主渠道，小程序订阅消息只作为用户授权后的补充。本文不扩大为营销群发，也不顺带重写私信 IM。

依赖 [支付设计](2026-10-24-delivery-payment-integrity-design.md) 和 [骑手结款设计](2026-10-24-rider-auto-payout-design.md) 的事件语义；站内/订单通知本身可先独立交付。

`backend/internal/module/delivery/dispatch_types.go` 已有 `delivery_outbox`、租约、重试和 `RiderPoolOpened`；`backend/internal/module/admin/deliverynotify/sender.go` 是企业微信群机器人，不是公众号。目前缺少通用收件人/渠道投递、公众号身份绑定和完整订单阶段事件。

## 2. 事件覆盖和收件人

以下事件名为本项目拟新增的领域契约，不是蜂鸟私有通知名或微信模板 ID。

| 业务事实 | 主要收件人 | 外发内容边界 |
|---|---|---|
| 外部订单通过验证并导入成功 | 订单所属商家 | 导入结果、订单公开单号；不能把 webhook 收到等同于建单成功 |
| 配送付款确认成功/需核实 | 付款商家 | 金额与真实状态；未知不能写支付失败 |
| `RiderPoolOpened` | 有资格、正在接单且开启新单提醒的骑手 | 限频、合并、过期判断；不是给所有骑手广播完整地址 |
| 订单被接取 | 商家、接单骑手 | 接单事实；其他候选骑手新单提醒停止 |
| 取货/配送中/送达 | 商家、当前负责骑手按相关性接收 | 状态变化，避免给操作者重复发送无价值外部通知 |
| 释放/转单/取消 | 商家及受影响的原/现骑手 | 使用已有合法状态转换；不新增转单业务 |
| 配送异常需处理 | 有处理权限的商家/骑手，必要时后台 | 异常摘要及受保护详情入口 |
| 退款受理、成功、明确失败 | 商家；影响骑手收益时通知本人 | “处理中”和“已退款”分开 |
| 收益核验完成、提现受理/待审核/拒绝 | 本人骑手 | 不将业务收入当作已经付款 |
| 等待微信收款、结款成功/明确失败 | 本人骑手 | 确认收款入口或真实结果 |
| 支付/打款通道停用、对账异常、投递积压 | 授权后台人员 | 脱敏诊断；不向全体用户广播后台错误 |

某事件没有适用公众号模板或不满足平台投递条件时仍保留站内消息，渠道标记具体不可发送原因。不能把任意事件塞进不匹配模板以宣称全部可推送。

## 3. 事务内事件，事务外投递

1. 订单/资金状态写入和 outbox 事件在同一数据库事务提交。事务回滚无事件，通知失败不回滚已成功的订单/付款。
2. 保留现有聚合 ID、版本与事件类型唯一约束，增加聚合种类/事件 schema 版本的兼容表达。历史 `RiderPoolOpened` 仍能处理。
3. 事件处理器持租约将一个事件展开为站内记录和收件人/渠道投递任务；展开成功即可完成事件，不等待所有外部渠道发送完。
4. 投递唯一键包含事件、用户、渠道；重复消费不重复建站内消息或渠道任务。各渠道独立重试，公众号失败不再次发已经成功的站内通知。
5. 渠道任务记录策略版本、身份绑定快照、模板版本、供应商消息 ID、错误类别、尝试次数、租约和过期时间。恢复绑定后不把旧私人消息发给新绑定的另一个人。
6. 通道未配置时状态为阻塞/未配置而非成功；可在配置恢复后重试仍有效的任务。用户拒绝、解绑、过期等记录为有原因的跳过，不在以后静默补发过时消息。
7. `accepted` 仅表示平台受理；`delivered` 仅在有可信回执时使用；`read` 只来自用户自己的站内已读动作。公众号未提供阅读证据时不伪造已读。
8. 外部渠道可能不支持业务幂等键；若发送后响应丢失，保存 `unknown`，利用可用回执核实。无法核实时不自动无上限重发，后台人工重试明确提示可能重复。系统不承诺外部 exactly-once。

## 4. 公众号身份绑定

- 小程序 `openid` 与公众号 `openid` 不通用。既有 `OrderNotice` 开关不是公众号授权，关注公众号也不能替代用户与本系统账户的绑定。
- 增加独立微信身份关联记录，键包含渠道 `appid` 与 `openid`；只采用可信微信返回的 `unionid` 在正确开放平台范围内关联，或使用已登录小程序发起的一次性绑定流程。
- 一次性绑定令牌短时有效、随机、单次消费，并绑定发起用户及会话；OAuth 回跳校验 `state`、固定回调域名和客户端身份。昵称、手机号相似不能作为自动合并依据。
- 关注、取消关注、授权撤销和账号注销更新绑定/可发送状态；回调验签、解密、时间窗与重放去重缺一不可，重复事件幂等。
- 一个渠道身份不能悄悄绑定到多个系统用户。变更绑定需当前登录账户确认，记录历史，停止旧绑定投递。公众号收信身份变更不改变微信收款身份。
- access token、AppSecret、回调 token/加密 key 仅保存在服务端安全配置；日志、浏览器、仓库和通知 payload 不含密钥。
- 公众号/小程序关联、模板列表、账号类型及发送权限必须在真实账号核验；没有官方合同和实际模板时不得臆造模板 ID、长期授权或跳转参数。

## 5. 通知偏好、时效与隐私

- 复用用户现有订单通知偏好，增加渠道可用性展示和主动订阅的新单提醒设置；骑手开启接单不自动取得公众号或订阅消息权限。
- 站内消息可查；关闭外部提醒或安静时段不伪造外部发送。确需即时提醒的订单类别需显式设置，不默认绕过用户静音。
- 新单提醒外发前再次核实订单可抢、骑手有资格/正在接单、地域范围和接单容量；已被接、已取消或超时则停止投递。
- 新单使用收件人级合并、速率限制和过期控制；不堆积后一次性轰炸。其他关键资金结果按事件保留，不与普通新单合并掉。
- 不外发手机号、完整宿舍地址、身份证或密钥。消息仅含必要的公开单号、简短状态/金额和安全详情入口。
- 点击通知进入现有订单/钱包详情后重新鉴权和查询最新状态；转单/取消导致权限失效时显示无权查看，不泄露旧订单内容。
- 客户端按账户、角色、聚合 ID、版本定向刷新对应订单、页签计数或钱包；忽略旧事件和其他角色事件。登出、切换账号、卸载页面时释放订阅。

## 6. 后台与代码职责

- outbox 保持在 `delivery` 领域；通用通知展开、收件人选择和渠道投递分离，不把公众号 SDK/HTTP 请求放进订单事务。
- 扩展 `admin/deliverynotify` 的适配器与 worker，不把现有 WeCom 群机器人改名当成公众号。
- 用户/微信身份模块负责绑定、授权、关注状态及 token 管理；通知模块只查询可投递身份。
- 后台提供事件、站内消息、渠道结果、积压/死信、脱敏失败原因与受控重试；禁止跳过权限把任意用户加入推送。
- 小程序继续使用现有导航与配色，补接通知列表/角标、绑定状态、偏好与详情跳转；不复制工作台、不增加假入口。
- 业务界面刷新失败提示重试，但不能撤回已经成功的付款/送达；关弹窗也不能制造成功状态。

## 8. 验收和上线顺序

自动化验收覆盖：事务回滚不发信、重复事件只建一次任务、单渠道失败不重发其他渠道、发送响应丢失、租约过期/多实例认领、积压恢复、未知模板、token 失效、解绑/退订/注销、OAuth 重放及绑定冲突、新单过期/已被抢、静音限流、跨角色/跨账号/越权跳转、通知内容脱敏、无可靠回执不标已送达/已读。

验收沿用支付设计的 Go/typecheck/构建，并保留 `node scripts/check-private-messaging.cjs` 与相关私信测试，确保通知补全不破坏原 IM。新增通知集成测试用隔离 MySQL 与 HTTP server；官方渠道真实发送验收只能在授权的测试账号/模板完成，不给真实用户群发测试消息。

落地顺序：先事件与站内记录，再公众号绑定和渠道，再小程序授权补充及后台可观测性。平台模板不具备时报告渠道未开通，站内功能仍可独立使用。生产启用、数据库迁移、后台发布和微信上传分别验收，不把设计文档或 mock 测试当作开通成功。
