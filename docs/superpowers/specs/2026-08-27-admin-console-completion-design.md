# 湛科生活圈后台管理补全设计

## 1. 目标与边界

本轮将隔离分支中的后台管理站从“视觉系统试验版”补全为可进行最终审查的运营后台。目标是修复布局错位、统一组件工艺，并把后端已经提供但前端尚未接入的管理能力补齐。

必须保持以下边界：

- 不新增或改变后端接口、鉴权策略、管理员权限、审核状态机和业务数据规则。
- 不伪造统计、用户、反馈、帖子、商品、举报或导航数据。
- 不实现后端尚未支持的搜索、批量操作、导出、举报直接结案或反馈状态流转。
- 不修改现有四个小程序脏文件，不合并到原项目分支，不部署。
- 数据库迁移只作为本地预览运行条件处理，不写入前端代码，也不作为已部署状态宣称。

## 2. 当前问题

### 2.1 布局与组件

- `apps/admin/src/styles.css` 同时保留多轮壳层、表格、面板和响应式规则，后定义规则覆盖前定义规则，造成内容宽度、账户区、表格和操作按钮在不同页面不一致。
- 多个页面各自实现 `Panel`、分页、按钮和表格容器，视觉与交互规则不统一。
- 表格操作把所有状态和角色动作同时平铺，扫描成本高，容易误操作。
- 英文枚举、时间原值和内部状态直接展示，缺少一致的中文语义层。
- 部分页面只有加载成功视图，加载、空态、错误和刷新路径不完整。

### 2.2 已有接口未完整接入

- `/admin/users`、`/admin/posts`、`/admin/products`、`/admin/reports` 支持分页，但前端固定读取第一页且没有分页控件。
- `/admin/feedbacks` 已存在，后台没有“用户反馈”入口。
- 普通导航分类与入口已经有创建、更新、删除接口，现有页面仍为只读。
- 举报的处置属于统一审核流程，但举报页没有清晰的“前往审核”衔接。
- 数据统计只展示四个数字，没有基于这些真实数字提供待办导航。

### 2.3 本地运行条件

- 当前本地数据库已具备管理员登录迁移 `035`，但外部商家目录依赖的 `031_external_takeout_merchant_directory.sql` 尚未应用，导致导航页出现“服务暂时不可用”。
- 该迁移属于后端仓库已有的正式迁移，不在前端伪造数据；应用前后都必须记录本地环境状态。

## 3. 信息架构

侧栏继续沿用三个现有分组，不增加后端没有支撑的模块：

1. 运营中心：媒体运营、配送运营，以及功能开关启用时的外卖运营。
2. 内容治理：统一审核、帖子管理、商品管理、举报审核、身份审核、用户反馈。
3. 平台管理：数据统计、用户管理、导航管理。

“用户反馈”作为独立入口加入内容治理。举报页保持证据查看和状态展示，实际审核仍进入统一审核，避免产生两套处置状态机。

## 4. 视觉与布局系统

### 4.1 页面壳层

- 桌面端侧栏宽度固定，主内容使用 `minmax(0, 1fr)`，顶部栏和正文共享同一内容边界。
- 顶部栏保留页面标题、说明和账户操作；账户信息在窄宽度时换行，不与标题相互挤压。
- 正文最大宽度统一，数据密集页允许使用完整可用宽度，不为不同模块设置互相冲突的宽度。
- 小于桌面断点时侧栏改为顶部横向导航；表格保留横向滚动容器，不压缩到不可读宽度。

### 4.2 设计令牌

- 保留当前中性深蓝灰后台基调，强调色只用于当前导航、主要操作和信息状态。
- 间距使用 4/8/12/16/24/32 的稳定节奏。
- 媒体和内容容器使用一致边框、圆角和层级，不继续叠加第二套阴影与面板规则。
- 状态色只服务于成功、警告、危险和信息语义；不可用状态降低对比度但保持可读。

### 4.3 公共组件

补全或统一以下组件：

- `AdminPanel`：标题、说明、工具区和内容区域的统一容器。
- `AdminToolbar`：筛选、结果总数、刷新和主要操作的统一行。
- `AdminPagination`：页码、总数、每页数量与前后翻页。
- `AdminBadge`：将后端枚举映射为中文标签和稳定状态色。
- `AdminRowActions`：只突出当前可执行动作；高风险动作必须确认。
- `AdminState`：加载、空态、错误、无权限和刷新入口。
- `AdminTableFrame`：统一表头、行高、首列信息层级、横向滚动和粘性操作列。

公共组件不得吞掉后端错误文本；页面需要同时提供友好的中文说明和可诊断的错误信息。

## 5. 页面设计

### 5.1 数据统计

- 保留真实总量与今日新增。
- 增加“待处理工作”区，只使用现有 `pendingReview` 和模块入口，不推算趋势。
- 提供前往统一审核、用户管理和导航管理的快捷入口。

### 5.2 用户管理

- 接入 `page`、`pageSize` 参数和统一分页器。
- 角色、状态改为中文徽标。
- 当前状态对应动作禁用；状态调整与角色调整分组显示，避免六个按钮平铺。
- 修改自己、最后一个启用超级管理员等服务端保护错误必须原样反馈。
- 禁言、封禁、降权和提升为超级管理员需要确认；成功后刷新当前页。

### 5.3 帖子与商品管理

- 接入分页、加载、空态和刷新。
- 标题、作者/卖家、业务状态、审核状态和编号建立固定列层级。
- 已通过内容提供带原因的下架操作；待审核内容提供前往统一审核入口；其他状态明确说明不可操作原因。
- 商品价格统一格式化，内部状态统一中文映射。

### 5.4 举报审核

- 接入分页并规范目标类型、原因、状态和时间格式。
- 举报处置继续依赖统一审核任务；页面提供前往统一审核入口，不新增举报结案接口。

### 5.5 用户反馈

- 新增只读反馈列表，接入现有 `/admin/feedbacks` 分页接口。
- 展示用户、分类、内容摘要、图片数量、提交时间和当前状态。
- 后端没有反馈状态修改接口，因此不提供“已处理”等虚假按钮。

### 5.6 导航管理

- 普通导航分类支持新增、编辑和删除；入口支持新增、编辑和删除。
- 编辑表单严格对应后端 `Category` 与 `Item` 字段，不增加营销配置。
- 删除前展示影响范围并二次确认，成功后重新读取导航树。
- 外部商家目录继续使用现有独立组件，统一表格、表单和错误状态。

### 5.7 其他现有模块

- 媒体、配送、外卖、身份与统一审核保留现有业务功能，仅迁移到统一壳层、工具栏、分页、状态和反馈组件。
- 不重写这些模块的数据流，不改变任何资金、配送、身份或审核操作。

## 6. 数据流与错误处理

每个列表页遵循相同流程：

1. 页面状态保存页码、每页数量和后端已支持的筛选条件。
2. 参数变化后请求现有接口，并用请求序号或取消标记防止旧响应覆盖新页面。
3. 写操作前按风险级别确认；提交期间禁用当前操作，防止重复请求。
4. 成功后保留当前筛选并刷新当前页；若当前页已无数据，则回退一页。
5. `401` 继续交由现有会话逻辑处理；`403` 明确显示权限限制；其他错误提供重试入口。

不在浏览器中保存管理员密码，不改变 CSRF 和 Cookie 处理方式。

## 7. 验证与验收

### 7.1 静态验证

- TypeScript 类型检查。
- 管理后台生产构建。
- 现有后台 UI、密码会话、身份审核、外部目录和业务边界检查脚本。
- `git diff --check` 和精确文件清单审查。

### 7.2 浏览器验证

- 使用真实管理员会话逐项打开全部导航模块。
- 验证加载、空态、错误、分页、确认弹窗和成功反馈。
- 桌面宽度验证侧栏、顶部栏、账户区、表格和操作列对齐。
- 真实窄屏 viewport 验证 `innerWidth`、`scrollWidth` 和表格容器边界，不只依赖截图判断。
- 导航页在应用本地 `031` 迁移后验证外部商家目录读取；不执行无必要的删除或业务状态写入。

## 8. 交付状态

实现提交保持在 `codex/campus-services-review` 隔离分支，不合并、不部署。交付时提供：

- 设计提交与实现提交。
- 修改文件清单。
- 构建和浏览器验证结果。
- 可查看的本地后台页面。
- 本地数据库迁移与预览管理员说明。
- 仍需真实生产配置或人工验收的事项。
