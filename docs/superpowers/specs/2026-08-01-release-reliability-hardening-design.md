# 湛科生活圈发布可靠性加固设计

日期：2026-08-01

## 目标

在不上传微信版本、不修改生产数据、不改变现有蓝白视觉与业务导航的前提下，把当前 `master` 收敛为一份可重复构建、可回归、可由用户在微信开发者工具中上传的本地发布候选版本。重点消除移动网络下的登录误失败、分页截断、写入重复、商家返回不刷新、审核状态分裂、骑手身份越权和生产配置误用。

## 方案比较

### 方案 A：只修当前可见故障

优点是改动少；缺点是分页、幂等和审核一致性仍会在数据量或弱网条件下重新暴露，不满足发布候选标准。

### 方案 B：发布可靠性收敛（采用）

沿用现有服务、页面与设计系统，按“客户端可靠性、服务端状态一致性、管理端可处理性、发布可追踪性”四条边界加固。每项改动均有聚焦测试，并以完整 `verify`、构建和后端测试收尾。该方案能修复已证实问题，又不会重新设计产品或扩大业务范围。

### 方案 C：重写状态管理和审核架构

长期可塑性最高，但会引入大范围迁移、回归和发布风险，不适合作为当前交付收尾。

## 设计边界

- 保留现有蓝白视觉、页面信息架构、角色入口和真实数据契约。
- 不新增广告、虚拟用户、虚拟订单、虚拟统计、假图片或静态业务回退。
- 不接入微信支付，不配置新的企业微信 Webhook，不写生产数据库。
- 不上传微信体验版或正式版；只生成本地构建产物与上传说明。
- 用户原有未跟踪计划文件不纳入提交。

## 1. 小程序客户端可靠性

### 1.1 登录与会话初始化

登录和 `currentUser` 使用独立的 12 秒超时；仅对网络错误和超时进行一次短抖动重试，HTTP 4xx、身份错误和业务拒绝不重试。继续使用现有 session epoch 防止旧请求覆盖新用户。

### 1.2 写入幂等

帖子评论与既有商品留言采用同一模式：首次提交生成 `clientRequestId`，同时发送 `Idempotency-Key`。网络失败保留请求 ID供重试；明确的 4xx 或成功响应清除待提交状态，避免客户端超时后产生重复评论。

### 1.3 分页与真实总数

搜索、帖子评论、商品留言、我的内容、用户公开主页、商家订单和骑手订单统一保留 `page`、`total`、`hasMore`、`loadingMore`。列表按主键去重；首次失败保留页面错误，后续页失败只显示可重试状态，不清空已有数据。只有 `items.length >= total` 时显示“到底了”。

### 1.4 页面生命周期与发布等待

商家工作台改用 `useDidShow` 刷新，并使用请求代次避免旧响应覆盖新响应。多图发布采用受限并发审核和整次提交总超时，页面明确区分上传、审核和发布状态，避免最多九张图片串行等待十余分钟。

## 2. 后端一致性与权限

### 2.1 骑手身份守卫

`/delivery/rider` 路由必须同时满足登录和 `IdentityRequired(user.IdentityRider)`。旧的直接激活接口不得再绕过正式申请、授权和审计链路；存量孤立记录仅输出诊断，不在本次自动改写生产数据。

### 2.2 审核原子性

内容状态与审核任务状态在同一 GORM 事务中完成；读取审核任务时加行锁或版本条件，重复或并发决定返回稳定结果。任何一步失败均整体回滚。

### 2.3 严格审核请求

审核决定拒绝畸形 JSON、未知字段和尾随内容。拒绝操作必须提供裁剪后的非空原因，并限制长度；通过操作不接受伪造的拒绝原因。错误使用明确 4xx 返回，不得吞掉解析错误后默认通过。

### 2.4 举报建单

举报记录与审核任务使用同一事务；写接口接收幂等键并建立唯一约束或等价查重，防止“举报存在但后台无任务”和重试重复举报。

## 3. 管理后台可处理性

身份/内容审核列表使用服务端 `total` 和分页，默认优先待审核与审核中状态；超过 20 条时仍可访问后续页面。操作期间锁定当前任务，成功后刷新对应页，失败保留选择和错误信息。空、加载、错误、无权限和处理中状态沿用现有组件风格。

## 4. 发布与运维硬化

- 增加 `/readyz` 检查数据库等关键依赖，保留 `/healthz` 作为进程存活检查。
- 增加不含秘密的版本信息（构建版本、Git commit、构建时间），便于判断线上是否为本地候选版本。
- 生产环境拒绝默认数据库 DSN和隐式默认监听配置；布尔环境变量只接受明确合法值。
- CORS 使用同源或显式白名单，不再组合 `*` 与 credentials。
- Node 版本约束与 Vite 8 对齐；Admin Dockerfile 使用 lockfile 和 `npm ci`；本地 compose 明确标记为开发用途。

## 错误处理原则

1. 网络失败只影响当前动作，不回退到假数据。
2. 分页失败保留已加载内容并允许重试。
3. 写入不确定时复用同一幂等键。
4. 审核、身份和权限失败默认关闭能力，不默认放行。
5. 生产依赖不可用时 readiness 失败，但 liveness 保持可诊断。

## 验收标准

1. 登录在正常移动网络波动下不再因 3 秒默认超时误失败。
2. 搜索和评论列表可加载超过 20 条，并显示服务端真实总数。
3. 同一帖子评论重放只产生一条记录。
4. 商家发布配送单后返回工作台立即刷新。
5. 未切换为已审核骑手身份时接单接口返回 403。
6. 并发审核或持久化失败不会产生内容与审核任务分裂状态。
7. 管理后台可处理第 21 条及之后的待审任务。
8. `npm run verify`、`npm run build`、后端聚焦测试与 `git diff --check` 通过。
9. `apps/miniapp/dist` 和 `apps/admin/dist` 不包含本地 API、测试凭据或静态假数据。
10. 不执行微信上传、不改生产配置、不写生产数据库。

## 批准记录

用户已明确要求“完全交给你解决”并要求不再逐项过问；本设计在上述安全边界内视为已批准，直接进入实施计划与实现。
