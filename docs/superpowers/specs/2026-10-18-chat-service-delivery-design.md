# 私信、服务与配送端体验设计

## 目标

在不改变现有身份守卫、业务接口和支付契约的前提下，减少私信等待感，统一学生服务入口，补齐商家与骑手工作台的触控操作，并明确支付、三方订单和通知的真实可用边界。

## 设计决定

1. 私信页面在会话关系建立后立即可输入；腾讯云 IM 的登录、历史消息和订阅在后台准备，不向用户显示“正在连接”。本地待发送消息立即进入消息流，发送成功后替换为云端消息；失败消息保留在原位置并显示“发送失败/重试”。不把失败伪装成成功。
2. 学生端“校园服务”只承载校内外卖商品展示和已配置的合作小程序商家目录。通用工具目录继续放在首页工具频道，服务页不再重复加载工具。
3. 商家和骑手工作台的底部导航继续点击可用，同时允许在同一工作台的订单分组之间左右滑动；手势只改变当前分组，不切换身份、不改变页面栈。身份切换保留单一入口。
4. 商家/骑手头像、封面优先使用已有真实资料；缺失时使用文字首字母/中性底色，不生成业务图片。
5. 微信支付继续走后端预支付与回调，客户端仅在取得真实参数时调用 `requestPayment`。淘宝闪购、京东外卖、美团外卖只有在官方授权、店铺绑定和适配器配置存在时才启用；否则展示未连接和人工录入，绝不制造自动导入成功。
6. 私信推送使用腾讯云 IM 的会话订阅；配送状态通知使用现有 outbox/企业微信 sender。微信订阅消息需要管理员在公众平台配置模板和用户授权，本轮只保留契约与状态，不向真实用户发送测试通知。

## 验证范围

- MiniApp：聊天输入/失败重试、服务页目录、商家/骑手订单分组手势、资料头像封面、登录和发布入口。
- Backend：现有支付单元测试、外部收件箱单元测试和 `go test ./...`；不使用生产数据库、不写入真实订单。
- 发布：只在隔离分支构建和生成上传包；微信开发版/体验版、后端部署和三方授权仍分别报告。

## 不在本轮假装完成的部分

没有淘宝/京东/美团的官方商户授权、签名密钥或回调地址时，不注册适配器、不接收未验证 webhook、不自动建单。支付配置缺失时保持明确的“未开通”，不启用 mock 代替真实支付。
