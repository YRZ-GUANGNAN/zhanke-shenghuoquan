# 配送阶段化工作台设计

日期：2026-10-16

## 背景

当前项目已有骑手、商家配送和履约凭证接口，分支 `codex/media-review-policy-20261015` 的跟踪源码处于干净状态。本次优化依据 `fengniao-rider-research` 主分支 `9babdc2` 的静态研究资料进行信息架构和反馈设计校准，不把研究仓库中的 URL、动作名、状态码或静态推断直接当作本项目接口合同。

## 目标

在不新增 API、数据库字段、权限、角色、状态或配送业务的前提下，让现有配送功能呈现清晰的阶段、动作和结果：

- 骑手能快速判断当前订单处于待抢单、待取货还是待送达阶段。
- 每个订单只展示当前可执行的主动作，处理期间只锁定该订单。
- 凭证上传、审核等待、履约提交、提交失败和可重试状态有明确反馈。
- 操作成功与后续列表刷新失败分开表达，不误报订单结果。
- 商家端的列表数量、状态、时间线和凭证只展示真实接口数据。
- 保留现有路由、身份守卫、rowVersion/CAS、接口路径和权限边界。

## 非目标

本轮不实现研究资料中当前项目没有接口合同的能力，包括地图导航、距离/定位校验、异常报备、转单、历史订单、接单偏好、自动接单、离线送达和新的配送角色。也不把旧 `takeout-rider` 的状态或服务与新 `delivery-rider` 混合。

## 设计方案

### 1. 骑手工作台

继续使用现有三个列表分组：`grab`（待抢单）、`pickup`（待取货）、`delivery`（待送达）。顶部保留真实的当前任务、可抢单和已结束数量；数量在请求完成前显示加载态，不显示虚构数字。

订单卡按固定顺序组织：

1. 订单短号和时间；
2. 当前状态与配送费；
3. 取货点 → 送达点路线；
4. 备注和隐私提示（仅有真实数据时展示）；
5. 消息、电话、释放等次要动作；
6. 当前阶段唯一主动作。

主动作沿用现有服务方法：`claimDeliveryOrder`、`startToPickup`、`markPickedUp`、`startDelivery`、`markDelivered`。不增加新的动作枚举。凭证动作在同一订单卡内显示“选择照片 → 上传中 → 审核中 → 提交中 → 成功/失败可重试”的反馈，但不把上传成功冒充履约完成。

### 2. 按订单的并发与刷新反馈

将当前全局 `busyOrderId` 的展示锁定语义改为按订单记录忙碌状态；某一订单处理时仅禁用该订单的相关动作，其他订单仍可浏览。接口仍使用原有 rowVersion/CAS。

每次动作分成两个结果层：

- 动作请求结果：由接口响应决定，成功时显示“已接单/已开始配送/凭证已提交”等明确结果。
- 列表刷新结果：动作成功后重新读取已有列表；若刷新失败，保留成功结果并显示“操作已提交，列表刷新失败，点击重试”，不得把刷新异常当成动作失败。

每次重新加载工作台时同步 `/delivery/rider/me`，保证停用或休息状态不会长期停留在旧页面。

### 3. 商家配送页与详情

保留创建配送单、我的配送单、支付、取消、联系骑手、凭证和时间线。列表的 pending/delivering/completed 数量只使用真实返回值，首次请求完成前显示 `—`。分页游标仍从第 1 页开始；原来的 `1/1/1` 是分页初值，并非订单总量，不将其改成 0。

详情继续使用现有的状态、阶段时间戳和私有凭证解析服务。联系骑手入口改用当前项目已有图标体系；凭证按“取货凭证/送达凭证”和真实状态展示。不存在的异常、转单或地图数据不创建占位内容。

### 4. 信息反馈与空态

- 首次加载：展示页面级加载状态，不显示空列表结论。
- 空列表：分别说明当前阶段没有订单及订单进入该阶段的真实原因。
- 局部失败：保留上一次列表数据，显示可点击重试提示。
- 网络/业务失败：沿用后端返回错误文案，必要时使用现有 toast；不猜测研究资料中的错误码。
- 凭证失败：明确区分选择失败、上传失败、审核失败和履约提交失败，允许重新发起当前安全动作。

## 数据与接口边界

只调用现有服务：

- `services/delivery-rider.ts`：骑手身份、抢单、阶段动作、释放、列表。
- `services/delivery-merchant.ts`：商家配送单创建、列表、取消、费用确认。
- `services/delivery-proof.ts`：凭证列表和短期地址解析。
- 现有支付和配送会话服务保持不变。

不修改请求 URL、HTTP 方法、字段名、rowVersion、权限守卫或身份切换逻辑。

## 验证方案

代码修改后依次执行：

1. `node scripts/check-rider-workbench-clarity.cjs`
2. `node scripts/check-role-workbench-ui.cjs`
3. `node scripts/check-merchant-home-clarity.cjs`
4. `node scripts/check-miniapp-business-closure.cjs`
5. `node scripts/check-feature-policy.cjs`
6. `npm run typecheck`
7. `npm run build:miniapp`
8. `git diff --check`

验收重点是：一单操作不锁全列表、真实数量不闪现虚假值、动作成功与刷新失败分层、凭证状态可理解、现有接口契约和身份守卫无变化。

## 风险与回滚

研究资料来自静态 APK，不能证明线上规则；任何需要新接口才能实现的状态都留在后续评估。若验证发现现有页面依赖全局锁定或某个样式契约，优先回退对应展示改动，不修改后端。所有变更只在当前隔离分支，原项目和其他未跟踪 `artifacts/` 文件保持不动。
