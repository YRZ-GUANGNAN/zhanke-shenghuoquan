# 配送支付、退款与真实资金核验设计

日期：2026-10-24。基线：`main` / `ded4c0455ae07a32991dc0f55f67cb67e3ebaef8`。

状态：依据用户确认的总体方向形成书面设计，待书面审阅；本文不是已实现或已开通的证明。

## 1. 范围与分工

用户已认可商家、骑手 UI，本阶段不重新设计工作台。沿用现有配送账本，依次完成三个可以独立验收的子项目：

1. 本文：真实支付、退款、查单补偿和账本资金来源。
2. [骑手自动结款与人工备用](2026-10-24-rider-auto-payout-design.md)：以真实可提现资金为前提。
3. [订单与资金通知](2026-10-24-delivery-notification-design.md)：消费已提交的业务事件，不影响资金事务是否成功。

代码按将具备微信支付能力来准备；运行时必须核验实际商户配置和权限。没有真实配置不得回退到 mock。这里只处理平台配送服务费及对应骑手报酬，不新增淘宝闪购、京东外卖、美团外卖餐费代收、平台间资金归集或通用资金托管。

## 2. 已核对的现状

- `backend/internal/module/admin/deliverypayment/provider.go` 已有 JSAPI 预支付、请求签名、支付/退款通知解析；没有主动查询支付/退款的 Provider 契约。
- `backend/internal/module/admin/deliverypayment/handler.go` 的 `payment()` 查询本地记录，并非向微信查单。
- `backend/internal/module/delivery/funds_model.go`、`funds_service.go`、`funds_repository.go` 已有商家充值、余额扣款、配送费结算、退款、幂等和行版本控制。
- 当前 `CompleteRefund(success=false)` 将记录置为 `refund_pending`，不是最终失败；但该布尔值仍无法区分微信处理中、传输未知与明确失败。
- 当前通知验签没有按 `Wechatpay-Serial` 选择/核对可信密钥，成功 API 应答没有完成验签；支付回调还需要核对业务主体、币种和付款身份。
- 既有 MySQL/mock 验收只能证明本地业务合同，不能当作真实微信扣款、退款或到账证据。

## 3. 模块边界与兼容性

- `delivery` 领域负责金额、账本、结算、退款状态转换与事务；不能直接发 HTTP 或读取微信密钥。
- 微信适配器负责签名、验签、加解密、创建/查询/关闭支付、创建/查询退款以及结果归一化。
- 补偿任务负责认领有租约的待核实记录，调用 Provider 后通过同一领域入口更新结果。
- 保留现有商家支付接口、完整公开 ID、`ClientRequestID`/`Idempotency-Key`、身份守卫和行版本合同；新增字段采用兼容扩展。
- 前端继续通过 `apps/miniapp/src/services/delivery-payment.ts` 和 `hooks/use-delivery-payment.ts` 获取服务端事实；现有页面只补真实状态与必要操作，不更改配色、导航或订单排版。

## 4. 可信结果与状态

所有金额用 CNY 整数分；金额由服务端订单/费用快照计算，不相信客户端声明的配送费或到账金额。

| 观察结果 | 服务端处理 | 客户端含义 |
|---|---|---|
| 微信预支付参数生成 | 保存参数与原交易号 | 可以调起付款，不表示已支付 |
| 客户端 `requestPayment` 返回 | 触发受限查单/刷新 | 正在核实支付结果 |
| 验签并核对业务身份后的支付成功 | 同一事务写支付、结算或充值流水、业务事件 | 已支付 |
| 网络超时、签名无效、新错误码 | 保存待核实状态，查原交易号 | 结果待确认，不提示重新付一笔 |
| 微信退款受理或处理中 | 保持退款占用并继续查询 | 退款处理中 |
| 微信退款明确成功 | 同一事务更新退款、结算与事件 | 已退款 |
| 微信退款明确失败 | 保存失败原因与处置入口 | 退款失败，不恢复为可重复消费资金 |

校验必须覆盖可信证书/公钥标识、签名、时间窗、解密算法、事件类型、`appid`、`mchid`、交易号、金额、币种，以及支付时留存的付款人身份。对某种官方通知未携带的业务字段，通过已绑定的本地快照或主动查询核实，不凭空要求不存在的字段，也不跳过整体身份核对。

回调先落持久化记录再响应；重复或迟到回调走同一幂等入口。已确认成功不得被旧失败结果覆盖。遇到相互矛盾的可信结果，隔离记录并告警，不自动再扣款或冲销。

## 5. 查单、重试与退款恢复

1. 发起请求前持久化业务号与不可变请求摘要。数据库事务内不调用微信网络接口。
2. 同一请求键重试返回同一支付/退款记录；同键不同金额或订单返回冲突。
3. 超时、断网、服务重启后优先查询原交易号。需要再次提交时使用官方允许的原号、原参数，不在结果未知时换号。
4. 支付超时关闭前先查单；关单操作未知时继续查单，不把本地计时器当作微信已关闭。
5. 退款使用显式状态结果替代内部 `success bool` 的含糊语义；保留兼容响应，并迁移旧 `refund_pending` 到“需查询核实”，不批量推断成功或失败。
6. worker 使用租约、CAS、有上限的退避和告警；多实例只能由有效租约持有者提交状态，租约过期仍不允许换业务号造成重复资金动作。
7. 查询和回调统一走金额核验及记账事务；两个渠道并发只能入账一次。
8. 后台提供查询原单、查看脱敏错误和对账差异入口，不提供直接把未知状态改成已支付/已退款的按钮。

## 6. 真实资金来源与骑手可提现依据

- 订单直接微信付款：关联已确认的真实支付记录与配送费结算。
- 商家余额付款：必须追踪被消费的真实充值资金份额；只有结算来源写着 `wallet` 不足以证明资金真实。
- 增加充值资金批次及订单消费分配记录，保留来源交易、已消费/已退款金额与唯一引用。分配和钱包扣减在同一事务，不能重复使用一份充值。
- 既有混合余额、来源未知或 mock 充值进入“来源待核验”；不能通过本次迁移改写成真实可提现收入。历史补录需依据可验证的微信账单并保留审计，不直接改余额数字。
- 不删除历史收入和今日单量；“历史业务收入”与“已核实可提现金额”分别显示，避免原数据被静默抹掉。
- 订单退款申请、收入核验、提现锁款必须对同一资金来源协调加锁。来源进入退款/争议时不再用于新提现；已经提交微信的转账先核实，不能自动从骑手账户强扣追回。
- 上线前对旧钱包、流水、结算、骑手收益做差额报告；不一致项单独隔离，不把差额自动补成充值。
