# 淘宝闪购官方订单适配器设计

日期：2026-10-24。基线：`main` / `8dc9af9b06ec5289405010fd02fd381a238a467d`。

状态：依照[共用官方接入设计](2026-10-24-external-platform-connection-design.md)形成的 Provider 子规格。尚未完成淘宝闪购服务商/商家资质、应用获权、门店授权、沙箱或生产联调。

## 1. 名称、范围与兼容性

产品展示使用“淘宝闪购”；为兼容既有数据库、接口和历史订单，内部 `SourcePlatform` 暂保留 `taobao`。不能仅为改名修改已上线枚举或唯一索引。未来若官方稳定标识要求变化，通过显示名/Provider 版本映射处理。

本适配器首期只接官方订单与消息能力，用于订单提示、权威回查和配送字段归一化。不接入商品、库存、营销、金融、聊天或非本项目所需的特权接口，不代收餐费或读取未经授权的数据。

## 2. 资质、应用和配置

淘宝闪购服务商平台公开说明提供订单履约、门店管理、消息和大量 API；部分详细文档与接口只有登录、资质审批和应用获权后可见。实际接入必须先确定应用类型：

- 商家自研应用：只服务账号所属商家/门店，按官方自研流程申请。
- 服务商应用：供多个独立商家授权，按官方服务商资质、协议、安全和保证金要求申请。

不能为绕过服务商资质，把多商家平台伪装成单商家自研应用。特权接口的 WAF、等保、门店规模等条件只在确实申请对应特权时适用；首期普通订单能力不主动扩大申请。

部署配置只保存真实获权后的引用：

- `TAOBAO_FLASH_APP_KEY`
- `TAOBAO_FLASH_APP_SECRET_REF`
- `TAOBAO_FLASH_API_BASE_URL`
- `TAOBAO_FLASH_AUTH_BASE_URL`
- `TAOBAO_FLASH_MESSAGE_CONTRACT_VERSION`

正式 `Key/Secret` 由平台审核后发放。示例值、旧饿了么教程密钥和浏览器抓取 Token 都不得用于生产。

## 3. OAuth 与商家/门店授权

实现独立 `TaobaoAuthorizationProvider`，按账号内当前 OAuth 文档处理：

1. 服务端创建绑定用户和本地商家的短时单次 state。
2. 只重定向到配置白名单中的官方授权地址，并请求最小必要 scope。
3. 回调校验 state、平台错误和固定 redirect URI；授权码仅服务端交换。
4. 校验 Token 响应的应用、商家主体、授权 scope、有效期和刷新能力。
5. 调用官方商家/门店查询接口枚举真实可授权门店，再由用户确认本地映射。
6. access/refresh token 使用认证加密保存；到期前由租约任务刷新。

若平台使用非标准字段或一次性授权 Token，按官方合同建类型，不强行套通用 OAuth 字段。Token 轮换必须原子保存新 access/refresh token；刷新超时先查询/重试原刷新请求允许的路径，不让迟到响应覆盖新版本。

scope 增减、商家撤权、Token 过期和应用审核状态分开记录。重新授权不能静默扩大 scope；前端明确展示新权限和受影响门店。

## 4. API 签名与网关客户端

实现 `TaobaoSigner`、`TaobaoAPIClient` 与 `TaobaoMessageVerifier`，三者不能假定共用完全相同的签名输入。

- API 请求按当前官方文档处理公共参数、业务参数、时间戳、Token、签名方法、字符集和编码。
- 消息回调按消息平台合同验签、解密和应答；不能用 API 网关签名算法猜测消息签名。
- 签名从不可变参数对象生成；序列化后的实际请求必须与签名输入一致。
- 用官方 SDK/文档给出的非秘密固定示例建立测试向量；缺少固定向量时，在沙箱用已授权应用双向验证后才启用。
- API HTTP 200 仍需解析平台业务码、请求 ID和子错误；未知响应形状视为合同变化并暂停自动化。
- App Secret、Token、授权码、签名串和原始顾客信息不得进入日志。

签名方法、Token 字段名、TTL 和错误码在应用获权前不写死到共用领域；Provider 包通过版本化配置选择当前已验证合同，未知版本 fail closed。

## 5. 订单消息接收与推拉结合

按官方“订单推拉”与消息文档实现：

1. 回调入口通过随机 `bindingKey` 解析本地绑定，但绑定 key 不能替代平台签名。
2. 保留验签需要的原始 body/Header/query，严格限制尺寸、字段数和编码。
3. 校验应用、商家/门店、topic/消息类型、消息 ID、时间窗和签名/加密。
4. 按平台消息 ID或合同规定的唯一键去重，将最小定位信息持久化。
5. 使用 Provider 专用应答在要求时限内确认持久接收。
6. worker 再用官方订单查询接口拉取完整权威订单，避免丢消息、缩略推送和字段变化。

定时补偿拉取只使用官方允许的游标/时间窗/分页能力，并为每个绑定保存独立 checkpoint。checkpoint 必须在该页订单全部持久化后推进；分页中途失败不跳页。推送和拉取命中同一平台订单/版本时只导入一次。

## 6. 归一化规则

- 官方完整订单号以字符串保存为 `sourceOrderId`，不截断为展示号。
- 官方稳定门店 ID映射为 `sourceShopId`，必须属于当前 Token 授权范围。
- 取餐号/流水号映射为 `pickupCode`，前导零与字母保持。
- 取货/收货联系人、地址和隐私号从权威订单读取，并记录隐私号类型与有效期。
- 商家备注、用户备注按业务含义分字段读取，最终只把配送需要的摘要写入 `Remark`；拒绝控制字符和超限文本。
- 平台创建/修改/取消/退款状态经显式表映射。未识别状态为 `unknown`，不按“新订单”兜底。
- 使用官方更新时间、状态序列或消息版本收敛乱序；没有可靠版本时冲突进入人工检查。

商品明细和平台价格不属于本次配送最小模型，不能为了 UI 展示复制全部订单。若后续业务确需商品核验，应另行定义数据最小化、保存期限和权限。

## 7. 创建、变化和取消

选择一个经官方文档确认且已经具备完整履约字段的订单阶段作为 `created` 候选，避免“下单”“商家确认”等多个消息重复建单。其余事件：

- 地址/联系人/备注变化：回查后形成版本化 `updated`。
- 订单取消或退款使配送不应继续：形成 `cancelled` 候选。
- 催单、出餐、退款申请等不直接等价于取消或新建，进入对应提示/异常通道。
- 取消先到、创建后到时保留 tombstone，不复活订单。

适配器只证明平台事实。`autoImport`、`autoDispatch`、真实配送费和本地履约阶段继续由共用协调器裁决。

## 8. Token、错误和恢复

错误分类至少包含：临时网络、平台限频、Token 过期可刷新、需要重新授权、scope 不足、应用未上线、门店不匹配、消息签名失败、未知合同和订单冲突。

- 对可刷新 Token 使用单飞租约；业务请求遇到授权失败最多触发一次刷新后重放允许幂等的查询。
- scope 不足或应用未上线不能无限刷新，绑定转 `reauthorization_required`/`suspended`。
- 平台限频按官方返回等待，队列按门店/应用分区，防止一个门店拖垮全部绑定。
- 拉取 checkpoint、消息收件箱和订单快照分别持久化，恢复时从最后完整提交点继续。
- 授权撤销后停止新查询和导入，清除/封存可用凭据，保留历史配送事实。

## 9. 测试与真实验收

自动化测试覆盖：

- OAuth state 伪造/过期/重放、redirect URI、跨商家授权、Token 轮换和撤权。
- API 与消息签名固定向量、编码、重复参数、错误应用/Token 和篡改密文。
- 推送/拉取重复、checkpoint 崩溃恢复、分页边界、乱序和取消先到。
- 订单号精度、前导零、门店错配、隐私字段、缺地址和未知状态。
- 限频、Token 失效、业务码失败、HTTP 成功但结构异常；日志不含 Secret/Token/电话/地址。

真实验收先使用官方测试环境或批准门店，验证授权、Token 刷新、消息订阅、订单查询、补拉、撤权和重新授权。开始时两个自动开关均关闭；通过影子比对后依次启用人工导入、自动导入和自动发单。
