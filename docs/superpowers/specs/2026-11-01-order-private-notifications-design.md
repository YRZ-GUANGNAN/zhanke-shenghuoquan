# 订单与私信双通道通知设计

日期：2026-11-01  
基线：`codex/experience-ui-wallet-20261101` / `106fc6e9974d726e0a15613527965ab4fc48ebf6`  
状态：设计已获用户确认，进入实施计划前的书面审阅。

## 1. 目标与边界

本轮只补齐“新订单通知 + 私信通知”的通知闭环，不重做现有 UI，不改变订单、支付、钱包、配送状态机和 Tencent IM 会话权限。通知采用两个独立通道：

1. 小程序内通知：作为必备基础通道，写入独立的 delivery notification inbox API；展示层可与社区通知列表聚合，但不把新事件混入现有社区 `/notifications` 枚举，避免破坏 `b-community.ts` 的 normalize/labels/跳转契约。它同时驱动消息入口角标、工作台受控刷新和订单/会话详情跳转。
2. 微信小程序订阅消息：作为用户主动授权后的外部通道。后端只有在真实 `openid`、真实模板 ID、有效 access token 和本次可用订阅额度均存在时才发送；没有这些条件时记录不可发送原因，不能伪造成功。

本轮不接公众号模板消息，不把企业微信群机器人当作用户通知通道，不新增营销群发，不保存私信正文，不发送真实测试消息。既有企业微信运维通知可以继续独立运行，但不能与新的用户通知任务竞争消费同一订单 outbox。

微信订阅授权必须由小程序内的用户点击触发 `wx.requestSubscribeMessage`；订单通知、私信通知和设置页偏好是三个不同概念。一次性订阅只消耗一次发送额度，不能显示为永久授权。

## 2. 现状约束

- `backend/internal/module/delivery/dispatch_types.go` 中已有 `delivery_outbox` 和 `RiderPoolOpened` 事件；`backend/internal/module/admin/deliverynotify` 当前是企业微信群机器人发送器。
- 当前 delivery consumer 会直接认领并终结原始 delivery outbox；若未配置 webhook，历史事件会被标记为 `skipped`。因此新的通知展开必须由单一展开器完成，之后原始事件只完成一次，企业微信和用户通知作为独立渠道任务。
- 社区站内通知位于 `notifications` 表和 `backend/internal/module/community`，其唯一键是社区的 recipient/actor/type/post/comment/product 坐标，不能承载订单版本或腾讯消息去重。配送通知应使用独立通知事件、收件箱和投递任务模型，通过站内查询 API 聚合展示，原 `/notifications` 社区接口保持兼容。
- `apps/miniapp/src/services/e-im.ts` 和 `delivery-im.ts` 目前提供前台 Tencent IM 监听；`subscribeDeliveryConversationUnread` 还没有应用级调用。后端保存账号映射和会话关系，但不保存 IM 正文。
- 设置页已有 `orderNotice`、`socialNotice` 和 `quietHours`，这些是用户偏好，不是微信授权凭据。

## 3. 方案比较与选型

### 方案 A：统一通知领域事件与双投递器（采用）

业务事务写入领域事件；单一展开器按照收件人、用户偏好和渠道资格生成幂等通知任务；站内投递器和微信订阅投递器独立认领、重试和报告状态。Tencent IM 可信回调只产生脱敏私信元数据，客户端负责实时体验和回前台补取。

优点是事务与投递解耦、单渠道故障不影响另一渠道、便于账号切换和审计；代价是新增任务表和 worker。该代价是当前订单/钱包已有 outbox 机制下最小的可靠扩展。

### 方案 B：在订单或发信请求内同步调用微信

实现量小，但微信超时会拖慢业务请求，失败无法可靠重试，重放可能重复发送，也无法处理私信可信来源。放弃。

### 方案 C：引入外部消息队列

可扩展性强，但需要新的基础设施、部署和运维契约，与本轮只补通知且保持现有部署形态的边界不符。暂不采用。

## 4. 统一通知模型

新增独立的通知任务/授权记录（实际表名按现有迁移命名规则确定），至少包含以下语义：

- `event_id`、`event_type`、`aggregate_type`、`aggregate_public_id`、`aggregate_version`；
- `recipient_user_id`、`channel`、`template_key`、`payload_version`；
- `status`：`pending`、`processing`、`accepted`、`delivered`、`read`、`unknown`、`retry_wait`、`blocked`、`skipped`、`deadletter`；
- `attempt_count`、租约 token/过期时间、下一次尝试时间、脱敏错误码、供应商消息 ID、创建/处理时间；
- 唯一键为“事件 × 收件人 × 渠道 × 稳定通知用途”，保证重复消费不重复创建任务；模板版本只作为不可变发送快照，替换模板不能让同一事件自动重发。

微信授权记录独立保存：系统用户、当前小程序 AppID、`openid`、模板键、授权结果、授权时间、额度消耗、撤销/失效原因。客户端授权结果通过一次性随机 nonce 幂等上报并限频；服务端用条件更新原子占用一次性额度，只有微信明确未发送/拒绝的结果才释放或失效额度，`accepted` 和 `unknown` 不回退。不能把 openid 写入日志、站内通知正文或前端响应，也不能把授权结果写回用户偏好字段冒充永久开通。

任务状态含义必须保持：`accepted` 只表示微信接口受理；`unknown` 表示发送请求结果不确定，禁止无上限自动重发；`blocked` 表示配置、授权或模板缺失；`skipped` 表示事件已过期、用户退订、静音策略或没有适用收件人；`delivered/read` 只有可信回执或用户站内动作才可记录。

## 5. 订单通知事件与收件人

### 事件来源

保留已有 `RiderPoolOpened`，并在订单/支付/配送状态事务中补充通用事件：付款确认、接单、取货、配送中、送达、转单、取消、异常、退款结果、收益核验、提现受理/拒绝/成功/明确失败。事件和业务状态在同一数据库事务提交；通知失败不能回滚已经成功的订单或支付。

支付成功事件必须接在 `delivery/funds_repository.go` 的 `PayOrderWithWallet`、`ConfirmWechatPayment` 共享结算事务之后，由 `dispatch_repository.go` 的 `transitionToReadyAndEnqueueTx` 统一产生；不能分别在 `admin/deliverypayment/handler.go` 的回调、reconciler 或前端补发。后续状态覆盖 `delivery/repository.go` 的 `Transition`、`proof_repository.go` 的 `CreateProofAndTransition`，以及 `funds_repository.go` 的 `RequestRefund`。每个事件使用订单公开 ID、订单版本和事件类型幂等，事务回滚不留通知。

### 收件规则

- `RiderPoolOpened`：只发送给符合配送资格、正在接单、在服务范围内、容量可用且开启订单提醒的骑手。发送前再次核验订单仍可抢；被接单、取消或过期后，未发送任务变为 `skipped`。
- 付款和订单状态：发送给订单所属商家；只有明确的支付成功、明确失败或需要核实状态才能使用对应文案，未知状态不能写成失败。
- 接单、取货、配送中、送达、转单、取消和异常：发送给商家与当前/受影响骑手，避免给无关候选骑手发送完整地址。
- 收益、提现和打款：只发送给本人骑手；不得把预计收入写成到账，不得把受理写成成功。

消息只含必要的公开单号、简短状态、金额或详情入口；不发送手机号、完整宿舍地址、身份证、私钥、AppSecret 或 access token。通知点击后进入现有受保护页面，再鉴权并重新查询最新事实，过期或越权安全返回。

## 6. 私信通知

### 可信事件来源

私信微信通知只由 Tencent IM 的服务端可信回调产生，不接受客户端“发送成功”作为外部推送触发依据。回调处理器必须校验腾讯配置的签名/应用标识、事件类型、发送结果、目标账号映射和供应商消息 ID，并按 `sdkAppID + 供应商消息标识 + 发送账号 + 接收账号` 幂等去重。后端只保存收件人、会话关系、未读数量、时间和脱敏摘要/跳转坐标，不保存消息正文，日志不记录原始回调 body。

普通 C2C 私信按“收件人 + 对端用户”合并未读，不按商品 relation ID 为同一对用户重复发送；配送 GROUP 会话按订单公开 ID、当前成员和只读/撤销状态独立处理，不能套用 C2C peer 去重。回调中的商品、会话和关系字段必须重新查询本地参与者关系、账号 active/双向拉黑状态和 feature flag，不能通过回调字段把被禁用的商品会话改成普通 user 私信。

### 离线/未读策略

默认在接收方仍有未读消息且不处于当前可见会话时，按短时间窗口合并一条微信订阅通知；正在阅读、已读回执确认或用户关闭社交通知时不创建外部任务。页面关闭、网络断开或客户端心跳缺失不能单独证明离线，服务端信号缺失时降级为站内通知，不冒充确定离线。

小程序端只保留一个应用级 IM 监听。首次登录、重连和回到前台读取 Tencent 会话未读快照，以快照为准而不是累加事件次数；账号切换、角色切换和退出登录会清空旧状态并拒绝旧请求回写。只有当前页面可见、会话已鉴权且消息已经展示时才调用已读接口。

## 7. 小程序接入

- 在现有设置或通知偏好入口增加用户主动点击的“订阅订单通知/订阅私信提醒”动作；进入页面、切换身份、发消息、支付回调都不自动弹授权。
- 使用服务端下发的已配置模板键映射到真实模板 ID；客户端只上报用户选择结果和模板键，不上报或持久化 AppSecret。
- 分别处理 `accept`、`reject`、`ban`、用户关闭弹窗和 API 异常；授权失败不阻塞下单、抢单、聊天或支付。
- 学生、商家、骑手消息入口沿用当前布局，只增加未读角标/受控刷新；工作台收到新订单事件后重新查询授权订单接口，不直接修改订单事实、不跳动分页、滚动位置或操作状态。
- 通知跳转只使用现有路由；进入目标页后再次鉴权和查询，不能把旧 payload 当作事实来源。

## 8. 后台与投递职责

通知展开器负责收件人选择、偏好/静音、事件时效、过期和任务幂等；站内投递器负责通知列表与已读；微信投递器负责 access token 缓存、模板字段校验、额度占用、接口结果分类、退避和死信；Tencent IM 回调处理器负责可信校验、脱敏元数据和去重。

保持领域边界：`delivery` 核心不能直接导入 user、im、community 或 HTTP；`deliverynotify` 不能直接依赖这些领域仓储。收件人资格、账号状态、订阅授权和会话关系通过组合根装配的 ports/函数接口提供，最终在 `backend/cmd/server` 组合。这样既能复用订单事务，又不会把微信 SDK 或 IM 回调耦合进配送核心。

微信 access token、AppSecret、回调 token/加密 key 只从服务端安全配置读取，禁止进入仓库、浏览器、前端 bundle、日志或测试输出。模板 ID 未配置、openid 未绑定、订阅已用尽、用户拒绝、模板失效、token 失效和接口限流必须有可观测的脱敏错误类别，并保留站内通知。

原 `deliverynotify.Consumer` 不得与新展开器同时认领同一原始事件。迁移期间应明确历史 `succeeded/skipped/deadletter` 不回补，新增事件从新展开器开始；既有企业微信运维通道单独保留。

## 9. 测试与验收

后端测试必须覆盖：事务回滚不产生通知；重复事件只创建一组任务；站内成功不被微信失败回滚；微信配置缺失、拒绝授权、额度耗尽、模板字段错误、token 失效、超时未知结果的状态分类；租约过期、多实例认领、退避和死信；取消/已抢/过期新单停止投递；私信回调签名、应用标识、供应商消息 ID 去重；正文不落库、不出日志；账号解绑、注销、角色切换隔离。

小程序验收必须覆盖：应用级 IM 监听只有一份；回前台补取未读快照；重复事件不重复角标；当前会话才标已读；旧账号事件不能回写新账号；工作台通知只触发重新查询；授权弹窗只能由用户点击触发；拒绝/关闭不影响主业务；通知跳转重新鉴权。

既有验收命令继续执行：

```powershell
npm --workspace apps/miniapp run typecheck
node scripts/check-private-messaging.cjs
node scripts/test-chat-service-delivery.cjs
node scripts/check-boundaries.cjs
Push-Location backend
try { go test ./... }
finally { Pop-Location }
npm run build:miniapp
git diff --check
```

真实微信发送只能在已授权的测试账号、真实模板和明确测试窗口中验收；本地 mock、浏览器预览、开发版上传或接口返回 `accepted` 都不能被报告为真实用户已收到。

## 10. 上线顺序

1. 先落地独立通知任务、站内事件展开和小程序应用级未读刷新，保持微信投递默认关闭。
2. 配置真实模板、openid 绑定和安全凭据后，仅对主动授权的测试账号开启微信 sender；先验证订单和私信各一条，不群发。
3. 验证后台积压、失败、未知结果和解绑/退订路径，再逐步开放角色开关。
4. 将代码构建、数据库迁移、后台部署、微信体验版上传、真实设备验收分别记录；任何一项未完成都不能宣称“微信通知已全部打通”。
