# 京东官方订单适配器设计

日期：2026-10-24。基线：`main` / `8dc9af9b06ec5289405010fd02fd381a238a467d`。

状态：依照[共用官方接入设计](2026-10-24-external-platform-connection-design.md)形成的 Provider 子规格。目标平台是 `open.jd.com` 京东商家开放平台；尚未取得本项目新平台应用、scope、商家授权、沙箱或生产联调结果。

## 1. 新旧平台边界

京东秒送旧开放平台 `opendj.jd.com` 已公开提示升级到 `open.jd.com`，并计划于 2026 年 Q4 下线。新实现遵循以下规则：

- 最终 Provider 只以新商家开放平台账号内现行合同为准。
- 旧平台的 `app_key`、OAuth、签名、消息订阅和返回格式只能作为迁移背景，不能直接复制为新平台实现。
- 若本项目未来存在旧平台存量应用，迁移使用独立、显式启用的 legacy adapter；新旧 Token、回调和幂等空间分离。
- 没有存量应用时不实现 legacy adapter，也不为“兼容”留下可误启用的旧签名路径。

内部枚举保留 `jd`，产品显示使用平台在当前官方资料中的正式名称；名称变化不修改历史来源键。

## 2. 接入身份与应用配置

按真实业务身份在新平台选择：

- 商家自研：本项目仅服务同一商家主体下门店时，按自研商家流程创建应用、授权、沙箱和上线。
- 开发者/服务商：为多个独立商家提供系统时，注册开发者/服务商、创建应用并由商家授权。

不能用单商家身份承载未披露的多商家 SaaS。服务商保证金、资质、安全和协议要求以申请账号当时页面为准。

获权后配置以下密钥引用和合同信息：

- `JD_MERCHANT_APP_KEY`
- `JD_MERCHANT_APP_SECRET_REF`
- `JD_MERCHANT_API_BASE_URL`
- `JD_MERCHANT_AUTH_BASE_URL`
- `JD_MERCHANT_MESSAGE_CONTRACT_VERSION`
- `JD_MERCHANT_ENVIRONMENT`（只允许明确的 sandbox/production 值）

生产不能指向旧 `opendj.jd.com` API host。配置校验发现旧主机、缺失合同版本或部分凭据时保持关闭。

## 3. OAuth、授权和 Token 生命周期

新平台适配器定义接口，但字段在账号内文档确认前不写死旧平台语义：

- `BuildAuthorizationURL(session)`
- `ExchangeAuthorizationCode(code, session)`
- `RefreshAuthorization(binding, expectedVersion)`
- `RevokeAuthorization(binding)`（平台支持时）
- `ListAuthorizedShops(binding)`

流程使用短时单次 state、固定 redirect URI和最小 scope。授权码只由服务端交换；access/refresh token 加密保存并通过 CAS/租约轮换。Token 响应必须核对应用、商家主体、scope、环境和有效期。

旧平台曾使用的授权码接收响应格式、Token 字段或续期机制不自动视为新平台合同。若迁移工具返回旧、新两套凭据，分别标明 Provider 版本，先在影子模式比对后切换，不能让两个 adapter 同时导入同一门店订单。

## 4. 新平台签名与客户端

实现版本化 `JDMerchantSigner`、`JDMerchantClient` 和 `JDMerchantMessageVerifier`：

- 签名算法、参与参数、排序、时间戳格式、字符集、摘要/加密方法全部取自新平台获权文档。
- API 调用与消息推送可能使用不同验签合同，不构建跨协议万能签名器。
- 旧平台常见的 `app_key`/`sign`/`timestamp` 形态只用于 legacy 测试夹具，不能成为新平台默认。
- 请求序列化、签名输入和实际 HTTP body/query 必须来自同一不可变对象。
- 响应校验 HTTP、平台业务码、request ID、商家/门店和订单号；未知字段可忽略，未知状态/合同版本必须隔离。
- 密钥、Token、签名和原始订单隐私不进入日志。

使用新平台官方 SDK或固定签名示例建立非秘密测试向量。若文档只在控制台可见，在内部实施记录中保存文档标题、版本、日期和向量来源，不复制真实密钥。

## 5. 消息订阅、回调与补偿查询

只有应用在新平台完成测试/上线并订阅生产消息后，能力状态才可标记 `callbackHealthy`。测试订阅成功不能推断会收到生产消息。

回调流程：

1. 以固定 Provider 路由和随机 `bindingKey` 定位绑定。
2. 保留原始请求，限制 body/query/header 尺寸和编码。
3. 按新平台合同校验应用、环境、商家/门店、topic、消息 ID、时间窗和签名/加密。
4. 持久化最小定位信息，按消息唯一键和摘要防重/防冲突。
5. 返回新平台要求的 HTTP 状态和 body；不能沿用旧平台或本项目通用 JSON 应答。
6. 异步使用官方订单查询接口回查完整订单，成功后才归一化和导入。

若新平台提供消息拉取、重放或订单增量查询，以官方游标实现补偿；否则通过订单查询核实已收到提示，并用监控发现长时间无消息。不能用频繁全量抓取绕过消息授权或限频。

## 6. 订单归一化

- 新平台完整订单 ID以字符串保存为 `sourceOrderId`，不使用展示短号或数值类型。
- 新平台稳定门店 ID映射为 `sourceShopId`，必须在当前授权商家范围内。
- 取餐码/门店流水号映射为 `pickupCode`，不承担幂等。
- 取货地址、收件地址、联系人和隐私号来自权威查询；标记隐私号有效期及降级状态。
- 平台订单状态和更新时间/版本通过显式映射表转换；未识别状态为 `unknown`。
- 配送备注做长度/字符校验；商品、价格、优惠、结算字段不无差别复制到配送模型。

若迁移期同一真实订单可能从旧、新平台收到，必须取得官方稳定关联字段并建立迁移映射；没有可靠关联时不做猜测合并，保持其中一个 adapter 影子运行并人工比对。

## 7. 状态与自动发单

由账号内订单流程确认哪个阶段具备完整且可履约的数据，再映射为内部 `created`。其余消息：

- 订单地址/联系人/备注变更：权威回查后形成 `updated`。
- 平台取消/退款导致停止履约：形成 `cancelled` 候选，并按本地阶段安全处理。
- 商家确认、催单、出餐、配送状态等若不代表创建/取消，不能映射为重复新单。
- 乱序消息按平台版本收敛，取消先到生成 tombstone。

Provider 不执行配送费扣款。只有共用 `autoDispatch` 门槛通过，才能从已验证订单推进到骑手池；平台餐费、京东结算与本项目配送费账本保持分离。

## 8. 迁移、错误和恢复

错误分类：

- 新平台临时网络/5xx和限频：有上限退避。
- Token 可刷新：单飞刷新后只重放安全查询。
- 商家撤权/scope 不足/应用未上线：要求重新授权或平台审核。
- 签名/合同版本不匹配：暂停 Provider，不能回退旧算法。
- 环境错配：sandbox Token 不得访问 production，直接拒绝。
- 门店/订单冲突：隔离并人工检查。

存量旧应用迁移时采用单门店切换：暂停旧自动导入、完成新授权、影子比对、记录切换水位、切换消息来源、确认无缺口后撤销旧 Token。切换失败恢复旧 adapter 时必须确保新 adapter 没有同时导入，避免双单。

## 9. 测试与真实验收

自动化测试覆盖：

- 新平台官方签名向量、错误版本、时间戳/nonce、消息篡改和旧签名误用。
- OAuth state、redirect URI、Token 轮换、scope、环境隔离和撤权。
- 生产/沙箱消息订阅状态、Provider 专用应答、重复/乱序/取消先到。
- 订单号精度、门店错配、未知状态、缺失履约字段、隐私日志检查。
- 限频、网络未知、worker 重启、补偿 checkpoint 和新旧迁移双写防护。

真实验收必须在新平台完成应用创建、商家授权、沙箱测试和上线步骤后进行。先关闭自动开关，验证消息和查询一致性；再按影子、人工导入、自动导入、自动发单逐级开放。旧平台测试结果不能替代新平台验收。
