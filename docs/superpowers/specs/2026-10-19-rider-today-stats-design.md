# 骑手今日收入与完成单量设计

## 背景

骑手工作台目前只显示当前订单分组数量和历史已结束总量，无法回答“今天完成了多少单、产生了多少骑手收入”。`completedTotal` 来自完成分组的分页总量，且包含取消单，不能改名复用。现有配送域已经在送达完成事务中写入唯一的 `delivery_rider_earning_records`，其中 `rider_fee_cents` 是骑手净收入，`created_at` 是收入产生时间。

本次参考蜂鸟众包静态研究资料中的通用信息节奏：阶段优先、订单内容与经营数字分层、数字采用紧凑同层摘要。只借鉴结构原则，不复制其品牌色、图标、文案或页面布局。

## 目标

- 在骑手工作台顶部任务摘要下增加“今日单量”和“今日收入”两个轻量指标。
- 统计只针对当前已认证骑手，按北京时间当天的收入记录聚合。
- 今日单量定义为当天已完成且已产生 earning 记录的配送单数。
- 今日收入定义为同一时间窗内 `rider_fee_cents` 的总和，包含待结算、已结算和已线下支付记录；它表示今日产生的骑手净收入，不等于当前可提现余额。
- 统计失败、尚未加载或后端暂未提供时显示 `—`，不显示虚假的零值。

## 数据与接口

新增只读接口：

```text
GET /api/v1/delivery/rider/stats/today
```

继续复用现有登录中间件和 `IdentityRequired(user.IdentityRider)` 守卫。接口按当前用户的 `rider_user_id` 查询 `delivery_rider_earning_records`，时间条件为 `[Asia/Shanghai 当日 00:00, 次日 00:00)` 换算出的 UTC 时间窗：

- `COUNT(*)` → `todayOrders`；earning 表每个配送单有唯一约束，因此不会重复计数。
- `SUM(rider_fee_cents)` → `todayIncomeCents`；无记录时数据库聚合值为 0，但前端只有在接口成功返回后才显示 0。

返回结构：

```json
{
  "date": "2026-10-19",
  "timezone": "Asia/Shanghai",
  "todayOrders": 3,
  "todayIncomeCents": 900,
  "definition": "当天已完成并产生骑手收入记录的配送单"
}
```

不复用管理端全局 stats，不复用旧 `/takeout/rider/wallet`，不修改订单状态机、支付流程或数据库表结构。若统计 reader 未配置，接口返回服务不可用，前端保留工作台正常使用。

## 页面与交互

- 在现有 `rider-grab-context` 下增加一行双指标，左侧“今日单量”，右侧“今日收入”。
- 使用现有蓝色设计令牌、现有字号和边界；不新增大卡片、头像、封面或钱包区。
- 首次加载与刷新期间保留已有订单内容，指标显示 `—`；统计失败显示 `—`，订单列表仍可操作。
- 统计请求与订单请求并行但相互独立；当前分组横滑、底部导航、下拉刷新和身份切换保持不变。
- 数字更新使用现有轻量进入动效或无动效降级，尊重 `prefers-reduced-motion`。

## 验证与边界

- 后端单测覆盖北京时间跨日边界、只统计当前骑手、收入求和和空结果。
- 前端契约/隔离测试覆盖成功数据显示、加载/失败占位、统计失败不影响订单列表，以及不把 `completedTotal` 当今日单量。
- 运行小程序类型检查、配送工作台静态检查和构建。
- 不上传微信、不上传 GitHub、不改动现有未提交业务文件。
