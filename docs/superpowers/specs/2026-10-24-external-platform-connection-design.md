# 外卖平台官方接入与自动发单设计

日期：2026-10-24。基线：`main` / `8dc9af9b06ec5289405010fd02fd381a238a467d`。

状态：用户已确认采用美团、淘宝闪购、京东官方开放平台接入，并要求平台来单后可自动导入、满足条件时自动发配送单。本文是书面设计，不表示平台资质、应用、密钥、店铺授权、沙箱或生产联调已经完成。

## 1. 目标与非目标

目标是在不改变既有商家/骑手工作台视觉和配送状态机基本语义的前提下，补齐一条可审计的官方接入链路：

1. 平台应用配置和门店授权。
2. 回调验签、重放防护、持久化收件箱和主动回查。
3. 平台订单归一化、商家/门店绑定和幂等导入。
4. `autoImport` 与 `autoDispatch` 两级策略。
5. 更新、取消、退款等后续事件的安全同步。
6. 失败恢复、后台处置、站内及微信通知衔接。

不采用抓包、模拟登录、读取第三方 App 通知、注入第三方客户端、共享商家密码或绕过平台授权。首期不代收三家平台的餐费，不替平台结算，不修改商品库存，不自动接单/拒单，不向平台回写配送状态，除非后续获得对应官方权限并形成单独规格。

## 2. 已有基础与实际缺口

仓库已有：

- `SourcePlatform` 已包含 `taobao`、`jd`、`meituan`。
- `ExternalOrderAdapter` 已定义 `VerifyAndNormalize` 边界。
- `/api/v1/delivery/external-orders/:platform/:bindingKey/events` 已预留回调入口。
- `delivery_external_inbox` 已提供平台/门店/事件去重、租约、重试、死信和人工检查状态。
- 新建事件可复用手工发单管线，生成 `pending fee payment` 的配送单；回调本身不会扣费或开放骑手池。
- 平台来源、完整平台订单号、门店号和取餐号已能持久化并展示。

缺口是：

- `deliveryRuntime.externalIntake` 尚未初始化，运行时能力仍关闭。
- 没有应用配置、授权会话、门店绑定、Token 加密与刷新任务。
- 没有美团、淘宝闪购、京东的真实 Provider adapter。
- 通用回调响应不是三家平台各自要求的应答合同。
- 当前只有 `created` 自动建单，`updated`/`cancelled` 会进入 `needs_review`。
- 没有主动回查、乱序收敛、授权失效恢复和自动发单协调器。

## 3. 总体模块边界

按职责新增模块，不能把平台 SDK、业务导入和支付混进同一个 handler：

| 模块 | 职责 | 禁止承担 |
|---|---|---|
| `deliveryplatform` | 应用配置、授权会话、门店绑定、Token 加密封装、能力状态 | 配送费扣款、订单状态迁移 |
| `deliveryprovider/meituan` | 美团授权合同、验签、回查、响应编码和字段归一化 | 淘宝/京东协议 |
| `deliveryprovider/taobao` | 淘宝闪购 OAuth、消息验证、回查和字段归一化 | 美团/京东协议 |
| `deliveryprovider/jd` | 京东新商家开放平台授权、验签、回查和字段归一化 | 旧平台协议永久兼容层 |
| `delivery` | 归一化订单、收件箱、配送单、费用/状态机和幂等 | 读取平台密钥或直接发平台 HTTP |
| `deliveryintake` | HTTP 尺寸限制、路由和 Provider 专用应答桥接 | 通用 JSON 成功替代平台合同 |
| `deliverydispatch` 协调器 | 根据策略、订单事实和资金事实推进自动发单 | 在回调请求事务里调用外网或扣费 |
| `deliverynotify` | 消费已提交事件并投递通知 | 以通知发送成功决定业务提交 |

`external_takeout_merchants` 是对外展示的商家小程序目录，不是平台订单授权表。两者不可复用表、主键或开关。

## 4. 数据与凭据模型

### 4.1 平台应用配置

应用级密钥只来自生产环境变量或部署环境的密钥管理服务，禁止写入数据库明文、Git、构建产物、前端配置、错误响应或普通日志。每个平台配置包含：

- 稳定的内部 `provider_app_key`，用于关联非秘密配置。
- 平台分配的应用标识、当前协议版本、回调基础 URL、启用状态。
- 密钥引用而非密钥值，例如 `secret_ref`/`signing_key_ref`。
- 配置版本、创建/更新审计、最近一次能力核验结果。

进程启动时只装配完整、合法且显式启用的 Provider；任一必要字段缺失时该平台保持 `not_configured`，不能启用半套配置或回退到示例密钥。

### 4.2 授权会话

`delivery_platform_authorization_sessions` 保存短时、单次消费的授权事务：

- 随机高熵 `state_hash`，不保存可直接重放的明文 state。
- 发起用户、目标本地商家、目标平台、目标应用。
- 固定回调地址标识、PKCE 信息（平台支持时）、创建/过期/消费时间。
- 发起前页面与最终重定向白名单；不接受客户端提交任意回调 URL。

回调必须同时校验 state、有效期、未消费、登录用户/本地商家关系和平台错误。授权码只在服务端换 Token；不能进入 URL 日志、浏览器持久存储或小程序本地缓存。

### 4.3 门店绑定与 Token

`delivery_platform_shop_bindings` 是唯一可信绑定来源，至少包含：

- 不可枚举的 `binding_key`，供回调路由使用。
- 本地 `merchant_user_id`、平台、平台应用和平台商家/门店稳定 ID。
- 平台店名/门店名快照，仅展示，不参与授权判断。
- `auto_import`、`auto_dispatch`、通知策略及策略版本。
- 授权 scope/能力快照、状态、到期时间、最近成功回查时间。
- Token 密文、密钥版本、刷新租约和并发版本；不保存明文 Token。
- 撤销、暂停、重新授权、操作者及原因审计。

Token 使用带认证加密的密文，数据密钥由部署密钥或 KMS 包装。数据库备份泄露时不能仅凭一张表还原 Token。解密只发生在 Provider 请求边界，明文不缓存到跨请求全局日志。Token 更新采用行锁/CAS；刷新 Token 轮换时只允许一个租约持有者提交，旧响应不能覆盖新 Token。

同一平台门店只能有一个有效主绑定指向一个本地商家。重新绑定、商家注销或授权撤销要停止新事件处理并保留历史订单来源；不能把旧订单静默转给新商家。

## 5. 授权和能力状态机

统一内部状态，但保留平台原始错误码的脱敏审计：

| 状态 | 含义 | 可执行动作 |
|---|---|---|
| `not_configured` | 应用配置不完整 | 仅后台查看原因 |
| `ready_to_authorize` | 应用配置通过自检，门店未授权 | 商家发起官方授权 |
| `authorizing` | 授权会话有效 | 等待回调/取消 |
| `active` | Token/门店/scope 可用 | 接收、回查和按策略导入 |
| `refresh_required` | 可刷新或需补充授权 | 暂停高风险动作，尝试受控刷新 |
| `reauthorization_required` | 刷新失败、scope 撤销或平台要求重授权 | 商家重新授权 |
| `suspended` | 管理员或自动风控暂停 | 不接收新导入，保留查询与审计 |
| `revoked` | 平台/商家明确撤销 | 终止 Token 使用，不删除历史 |

配置存在不等于能力可用；能力接口必须分别报告 `configured`、`authorized`、`callbackHealthy`、`queryHealthy`、`autoImportEnabled` 和 `autoDispatchEnabled`，以及不含秘密的阻塞原因。

## 6. 回调接收、验签与主动回查

### 6.1 接收顺序

1. 由固定平台路由和不可枚举 `bindingKey` 找到当前有效绑定，不相信 payload 中的本地商家 ID。
2. 在 Provider 规定的原始字节、参数顺序/编码和 Header 语义上验签；禁止先反序列化再重组签名串。
3. 校验时间窗、随机数/消息 ID、应用/开发者 ID、门店 ID 和回调类型；敏感比较使用常量时间函数。
4. 建立回调尝试记录并按平台事件 ID 去重。没有稳定事件 ID 时，按官方稳定字段构造 Provider 专用幂等键，不能用接收时间随机生成。
5. 只保存经过最小解析且可审计的必要原始摘要和规范化事实；联系人等隐私不得写日志。
6. 在平台时限内返回 Provider 专用成功/失败应答。应答成功只表示已持久接收，不表示已建配送单、已扣款或已派发。
7. worker 在事务外调用官方订单查询接口回查完整订单，再把可信快照交给 `ExternalIntake`。

验签失败不进入业务收件箱；可记录不含 payload/签名的安全计数、平台、绑定哈希和请求追踪号。连续失败触发限频与告警，不在错误响应中暴露签名计算细节。

### 6.2 推送加查询的收敛模型

回调只是变化提示。每个平台适配器要提供：

- `VerifyCallback`：验证回调真实性并提取最小定位信息。
- `AcknowledgeCallback`：生成平台要求的 HTTP 状态、Header 和 body。
- `FetchOrder`：用绑定 Token 和完整平台订单号查询权威订单快照。
- `NormalizeOrder`：将平台快照映射到内部版本化结构。
- `ClassifyError`：区分重试、限频、授权失效、永久拒绝和合同变化。

查询请求必须有超时、退避、抖动、限频和断路保护。Provider 的成功响应也要校验业务码、门店归属和订单号，不以 HTTP 200 单独视为成功。平台不允许查询或暂时不可用时，事件保持 `awaiting_verification`，不能用未核实的推送内容自动扣费。

## 7. 归一化订单版本与隐私

当前 `ExternalOrderEvent` 继续作为配送所需的最小边界，但新增版本化的权威快照，至少保存：

- 平台、平台应用、平台门店 ID、完整平台订单 ID。
- 事件/平台订单版本或可比较更新时间。
- 平台订单状态、取消/退款标志及发生时间。
- 取餐号、取货联系人/地址、收件联系人/地址、备注。
- 字段完整性、隐私号/降级号类型、可用期限。
- 快照摘要、Provider 合同版本和查询时间。

原始商品、价格、顾客隐私和平台结算字段不因“以后可能需要”而全部复制。首期配送单只消费履约必要字段。平台隐私号按用途和有效期处理，不暴露给无关骑手或后台列表；平台推送数据不得被当作餐费结算依据。

版本比较以平台可验证的版本号/更新时间为主，接收时间只用于排队。同一订单的新旧事件乱序时，旧版本记为 `stale` 而不是覆盖新事实。不能比较的冲突进入人工检查。

## 8. 自动导入与自动发单

### 8.1 两级开关

- `autoImport=false`：只验证并保存待导入订单，商家确认后创建配送单。
- `autoImport=true, autoDispatch=false`：自动创建 `pending fee payment` 配送单，商家确认付款或使用现有合法余额。
- `autoImport=true, autoDispatch=true`：只有全部门槛通过，才自动支付配送费并开放骑手池。
- `autoDispatch=true` 必须隐含 `autoImport=true`；关闭导入时同时阻止新自动发单，但不回滚已创建订单。

策略变化使用版本号。每个外部订单保存创建时使用的策略版本，避免管理员切换开关与 worker 并发时产生不确定结果。默认安全值为两个开关均关闭；首次授权后由商家显式开启。

### 8.2 自动发单门槛

自动发单协调器必须同时确认：

1. 门店绑定仍为 `active`，平台订单经主动回查且属于该门店。
2. 订单是可配送的新单，取送地址/联系人完整，未取消、未退款、未进入冲突状态。
3. 本地商家身份与配送功能有效，费用策略已取得服务端快照。
4. 外部订单唯一约束未命中另一配送单。
5. 商家已明确启用 `autoDispatch`，单笔/日限额和风控规则通过。
6. 配送费有真实、可核验的支付来源；沿用[配送支付设计](2026-10-24-delivery-payment-integrity-design.md)，不能从未知历史余额或 mock 资金扣除。
7. 同一事务完成费用占用/扣款、配送单状态推进和 outbox 事件；外部网络调用不在该事务内。

任一条件不满足时保留订单并给出稳定原因，例如 `merchant_confirmation_required`、`insufficient_verified_balance`、`authorization_expired`、`incomplete_fulfillment_data`、`source_conflict`。不能为追求自动化而补造地址、电话、费用或订单状态。

## 9. 更新、取消和退款事件

- 未创建配送单：只更新权威快照；取消事件形成 tombstone，迟到的创建事件不得复活。
- 已创建但尚未开放骑手池：可信地址/备注更新可通过版本化命令同步；取消按既有配送退款状态机处理。
- 已开放骑手池但无人接单：停止继续派发并走受控取消/退款，通知商家。
- 已被骑手接单但未取货：不能静默删除，进入既有释放/异常处理流程并通知双方。
- 已取货或已送达：平台取消/退款只形成异常或对账事件，不自动撤销真实履约、强扣骑手收益或改成未送达。
- 平台状态与本地人工操作冲突时，以事实版本、状态机和审计为准进入 `needs_review`，禁止最后写入者覆盖。

首期只有在对应状态转换测试、支付退款链路和通知链路完成后，才允许将 `updated`/`cancelled` 从当前人工检查路径逐步放开。

## 10. 失败恢复与运维

- 回调接收、主动回查、Token 刷新、导入和自动发单使用不同队列/租约，互相失败不伪造整体成功。
- 每类任务保存稳定幂等键、尝试次数、下一次时间、最后错误分类和租约；不保存含 Token/联系人/完整 payload 的错误文本。
- `401/授权失效` 触发一次受控刷新；并发请求等待同一刷新结果。刷新明确失败转 `reauthorization_required`，不能无限重试旧 Token。
- 限频按 Provider `Retry-After`/官方错误码处理；没有明示时使用有上限指数退避和抖动。
- 合同解析失败、未知状态、门店错配和同事件不同摘要进入隔离，不自动重放。
- 后台可查看平台、门店、脱敏订单号、阶段、原因、重试时间和策略版本；可触发“重新查询原单”，不能直接改成已验证/已付款/已派发。
- 指标至少覆盖回调验签失败、持久接收延迟、查询成功率、Token 刷新、导入延迟、自动发单成功/待处理、死信和通知积压。日志使用内部追踪号，不记录密钥、Token、授权码、签名、完整电话和地址。

## 11. 接口与界面

商家端只暴露其有权管理的门店：

- 查询平台连接状态、能力和门店列表。
- 发起授权、完成授权后的门店映射、重新授权和解除绑定。
- 设置 `autoImport`/`autoDispatch`、限额和通知偏好。
- 查看待导入、待支付、待处理、已导入和冲突记录。
- 对允许的记录执行确认导入、支付/发单、重新查询和取消。

后台用于应用级配置状态、绑定审计、Provider 健康、死信和异常处置，不向普通管理员显示密钥/Token。所有写操作沿用管理员权限、CSRF、原因、版本/CAS 和审计。

平台回调路由改为 Provider 专用 handler 或响应编码器；不能让所有平台共用当前 `response.OK`。现有旧 URL 可在正式启用前做兼容路由，但不能在不同 Provider 之间共享签名协议。

## 12. 安全与数据生命周期

- 回调 URL 全程 HTTPS，固定域名、固定路径；反向代理必须保留验签所需的原始 URI/Body，且不记录敏感 query。
- 授权和回调接口分别限频；绑定 key 足够随机，但不能替代签名。
- 网络出口限制到官方域名；重定向不自动跟随到未知主机，防止 SSRF 和 Token 泄露。
- Provider HTTP 客户端设置连接/请求超时、响应体上限、TLS 校验和安全代理策略。
- 解除授权后立即停止 Token 使用并清理可撤销凭据；历史绑定、订单来源和审计按业务/合规期限保留，敏感快照按最短必要期限脱敏或删除。
- 账号注销、商家身份撤销、门店转让分别有显式流程；不能只删前端入口。

## 13. 分阶段启用门槛

1. **合同阶段**：取得平台开发者/商家资质、应用和真实账号可见文档；记录文档版本与 scope，不填示例密钥。
2. **离线阶段**：实现 Provider 单元测试、签名固定向量、恶意/重复/乱序样例、Token 加密和状态机测试。
3. **沙箱阶段**：仅接测试门店，`autoImport=false`、`autoDispatch=false`；验证授权、回调、回查、撤销和限频。
4. **影子阶段**：生产授权但只比对平台订单，不创建配送单；观察遗漏、延迟和字段完整性。
5. **人工导入阶段**：允许商家确认导入，仍不自动扣费。
6. **自动导入阶段**：按单门店、小流量启用，自动发单关闭。
7. **自动发单阶段**：支付、退款、通知、限额、暂停开关和对账全部通过后，按门店逐步启用。

每个阶段有独立回退开关。回退只停止新动作，不删除已接收事件、不改变已支付/已接单订单的事实。

## 14. 测试与验收

共用层自动化测试必须覆盖：

- 授权 state 伪造、过期、重复消费、跨用户/跨商家、开放重定向。
- Token 密文篡改、密钥轮换、并发刷新、旧响应覆盖和日志泄露检查。
- 签名错误、时间窗、重放、超大 body、同事件不同摘要和绑定错配。
- 回调成功但回查失败、回查成功但导入事务失败、worker 崩溃恢复。
- 乱序 created/updated/cancelled、取消先于创建、旧版本覆盖、未知状态隔离。
- 自动导入/自动发单开关并发、限额、余额不足、未知资金和重复扣费防护。
- 商家隔离、后台权限、CSRF、脱敏、注销/撤权和历史订单可追溯。
- Provider 未配置或合同变化时能力正确关闭；不能把模拟 adapter 加载到生产。

真实验收分别记录平台应用、测试门店、授权 scope、回调/查询证据、订单 ID 脱敏值和时间。不执行真实验收时只报告代码/沙箱结果，不能宣称三端已打通。
