# 首页真实工具、身份审核与真实账号设计规格

日期：2026-07-19
状态：用户已批准
范围：MiniApp 首页与“我的”、身份申请与 Admin 审核、微信真实登录切换

## 1. 背景与目标

当前 MiniApp 存在四个相互关联的问题：

1. 首页使用自定义导航栏，但右上搜索按钮没有读取微信胶囊按钮的实际位置，在部分机型和开发者工具中发生重叠。
2. 首页仅有“私信”“发现”，用户希望保留两者并增加“工具”；现有工具页虽然读取后台数据，但当前数据包含 `legacy-missing-appid` 占位项，不能作为真实工具展示。
3. “我的”页面可以切换学生、骑手、商家身份，但骑手缺少申请入口，商家目前又被后端默认视为可用，未形成真实、可审核的身份开通流程。
4. 本地后端当前启用 `ALLOW_MOCK_WECHAT_LOGIN=true` 且没有微信凭据，登录 code 被拼成 `mock_openid_<code>`，导致同一微信用户可能得到不同数据库用户号。

本次目标是在不重做整体 UI 的前提下完成以下闭环：

- 首页顶部为“私信｜发现｜工具”，并始终避开微信胶囊。
- 工具仅展示后台配置的真实小程序跳转项，不使用静态或占位数据。
- “我的”上半部分可直接进入资料编辑。
- 骑手和商家均通过独立申请、管理员审核后获得身份。
- 身份权限由后端强制执行，不能通过篡改前端绕过。
- 正式测试和发布使用真实微信 OpenID，并向用户展示稳定的数据库用户号。

## 2. 非目标

- 不重做首页、“我的”或工作台的整体视觉设计。
- 不重新启用旧外卖买家、菜品、订单、支付或旧工作台入口。
- 不展示、下发或记录到前端日志中的 OpenID、AppSecret 等敏感凭据。
- 不自动合并或删除现有 `mock_openid_*` 用户。
- 不在本次范围内提供用户自行注销骑手或商家资格。
- 不把工具增加为第六个底部导航项。

## 3. 已确认的用户体验

### 3.1 首页顶部与微信胶囊安全区

首页继续使用自定义导航栏。页面启动时读取 `Taro.getMenuButtonBoundingClientRect()` 和窗口信息，计算：

- 顶部状态栏和胶囊纵向位置；
- 胶囊左侧可用宽度；
- 搜索按钮与胶囊之间的最小安全间距。

顶部左侧依次显示“私信”“发现”“工具”，右侧保留搜索按钮。若运行环境无法返回胶囊数据，使用保守的默认右边距和顶部高度，不能回退到当前会重叠的固定定位。

### 3.2 工具页签

“工具”作为首页内部第三个页签，不改变底部五项导航。进入页签后请求现有 navigation 公共接口，并在服务层执行真实性过滤：

- 后台状态必须为启用；
- `appId` 和 `path` 均不能为空；
- 排除 `legacy-missing-appid` 等已知占位值；
- 排除专属于外卖商家目录的 `systemKey=external_takeout_merchants`；
- 不能在接口失败或空结果时补静态演示卡片。

三种页面状态：

- 加载中：显示轻量加载状态；
- 空结果：显示“暂无可用工具”；
- 加载失败：显示明确错误和“重试”。

点击真实工具调用 `Taro.navigateToMiniProgram({ appId, path })`。跳转失败时显示微信返回的可理解错误，不假报成功。

现有独立 `pages/tools` 页面不再作为入口；其可复用逻辑迁入首页工具页签，旧页面是否删除由实施阶段的引用检查决定。任何删除都不得影响其他已注册路由。

### 3.3 “我的”资料编辑入口

“我的”上半部分的头像、昵称、用户号和资料摘要组成一个可点击区域，点击后进入现有 `/pages/edit-profile/index`。现有“编辑资料”按钮可以保留为显式提示，但需要阻止嵌套点击造成两次导航。

页面继续显示 `profile.id` 对应的数据库用户号，不显示 OpenID。

### 3.4 身份申请流程

学生身份始终可用。点击未开通的骑手或商家身份时，进入统一身份申请页，而不是仅显示 Toast。

骑手申请字段：

- 真实姓名；
- 手机号；
- 必要证明图片。

商家申请字段：

- 负责人真实姓名；
- 联系电话；
- 商家名称；
- 商家地址；
- 必要证明图片。

字段长度、手机号格式、图片数量和图片归属均由后端再次校验，前端校验只用于即时提示。证明图片复用现有真实媒体上传链路，申请仅保存已完成并归当前用户所有的媒体资产 ID。

申请状态：

- `pending`：已提交、等待管理员审核，不允许重复提交或进入工作台；
- `approved`：身份已开通，可以切换并进入工作台；
- `rejected`：展示拒绝原因，允许用户修改后重新提交。

重新提交将同一身份的当前申请更新为 `pending`，同时写入新的审核事件；不允许同一用户同一身份并存多个当前申请。

## 4. 数据模型

新增迁移建议编号为 `034_identity_application_review.sql`，包含以下四张表。

### 4.1 `identity_applications`

每个用户、每种角色保存一条当前申请：

- `id`、`application_public_id`；
- `user_id`；
- `role`：仅 `rider` 或 `merchant`；
- `status`：`pending`、`approved`、`rejected`；
- `real_name`、`phone`；
- `merchant_name`、`merchant_address`，骑手申请时为空；
- `review_reason`；
- `reviewer_user_id`、`reviewed_at`；
- `submitted_at`、`row_version`、`created_at`、`updated_at`。

约束：

- `(user_id, role)` 唯一；
- 角色和状态使用数据库约束或等价的严格校验；
- `row_version` 用于提交和审核的乐观锁；
- `reviewer_user_id` 关联真实管理员用户。

### 4.2 `identity_application_assets`

保存申请与证明媒体的关联：

- `application_id`；
- `asset_public_id`；
- `sort_order`；
- 创建时间。

同一资产在同一申请内不得重复。服务层必须验证资产存在、上传完成且所有者为申请用户。

### 4.3 `identity_application_events`

保存不可覆盖的审核轨迹：

- `event_public_id`、`application_id`；
- `actor_user_id`；
- `event_type`：`submitted`、`resubmitted`、`approved`、`rejected`；
- 事件发生时的状态、原因和必要快照；
- 创建时间。

事件表只追加，不更新历史事件。

### 4.4 `user_identity_grants`

身份授权独立于旧外卖运行时：

- `user_id`、`role`；
- `status`：`active` 或 `suspended`；
- `source_application_id`；
- `row_version`、授权和更新时间。

`(user_id, role)` 唯一。学生身份不写入此表，由用户域固有提供。

迁移只回填有明确真实业务资格的旧记录：

- 现有有效骑手记录回填骑手授权；
- 已创建真实配送单的 `merchant_user_id` 回填商家授权；
- 不为全部历史用户批量授予商家身份。

回填必须是前向、幂等的，并在独立临时数据库中验证；不得在共享 `campus_circle` 上执行破坏性回滚验证。

## 5. 后端服务与权限

新增独立 identity-application 模块，负责申请、审核事件和身份授权。它不能依赖旧外卖订单、支付、菜品或买家服务。

用户接口沿用现有 `/auth` 用户域前缀：

- `GET /api/v1/auth/identity-applications`：返回当前用户两种身份的申请状态；
- `GET /api/v1/auth/identity-applications/:role`：返回某一种申请详情；
- `PUT /api/v1/auth/identity-applications/:role`：首次提交或被拒后的重新提交，要求 `expectedRowVersion`；
- 现有 `GET /api/v1/auth/identity` 继续返回当前身份及可用身份，不新增重复的身份授权查询接口。

管理员接口：

- `GET /api/v1/admin/identity-applications`：按角色、状态、页码筛选；
- `GET /api/v1/admin/identity-applications/:applicationPublicId`：查看详情和事件；
- `POST /api/v1/admin/identity-applications/:applicationPublicId/approve`；
- `POST /api/v1/admin/identity-applications/:applicationPublicId/reject`。

审核命令必须包含 `expectedRowVersion`。拒绝必须提供非空原因。管理员不能审核自己的申请。

审核通过使用单一数据库事务完成：

1. 锁定并校验申请仍为 `pending` 且版本一致；
2. 写入或激活 `user_identity_grants`；
3. 骑手申请通过时，通过共享的 Rider Identity 能力建立配送工作台所需的真实骑手资格记录；
4. 更新申请为 `approved`；
5. 写入审核事件。

任一步失败必须整体回滚，不能出现“页面已通过但工作台仍不可用”的半完成状态。

现有 `IdentityEligibility` 改为读取身份授权：

- 学生始终可用；
- 骑手要求有效骑手授权和有效骑手资格；
- 商家要求有效商家授权；
- `pending`、`rejected`、`suspended` 均不可切换。

工作台路由和业务接口继续执行后端授权检查，不能只依赖 MiniApp 的身份守卫。

## 6. Admin 审核界面

Admin 增加“身份审核”入口和列表，不改变无关页面布局。列表展示申请编号、用户号、角色、申请人或商家名、提交时间、状态。

详情页展示全部申请字段、证明图片和审核历史，并提供：

- 通过：二次确认后提交；
- 拒绝：必须填写拒绝原因；
- 已处理记录：只读显示，不重复提供审核按钮。

若版本冲突，Admin 提示“该申请已被其他管理员处理”，刷新最新状态，不覆盖已有结果。

## 7. 真实微信登录与稳定用户号

MiniApp 保持 `wx.login`。后端必须配置与项目一致的真实 `WECHAT_APP_ID` 和 `WECHAT_APP_SECRET`，调用微信 `jscode2session` 获取 OpenID，然后按 OpenID 查找或创建用户。

配置要求：

- `ALLOW_MOCK_WECHAT_LOGIN=false`；
- `WECHAT_APP_SECRET` 只存在于本机或服务器机密环境，不写入源码、规格示例值、日志或 Git；
- 生产环境继续拒绝 mock 登录；
- API 响应只返回稳定的数据库用户 ID，不返回 OpenID。

现有 `mock_openid_*` 用户处理原则：

- 不自动推断其与真实微信用户的关系；
- 不自动合并或删除；
- 生成只包含用户号、关联数据数量等非敏感信息的检查报告；
- 无关联数据的 mock 用户只能在单独确认后清理；
- 有帖子、商品、聊天或订单等关联数据的用户，必须经过管理员确认归属并使用独立迁移方案处理。

真实微信凭据未配置前，代码构建和自动测试可以完成，但“同一微信账号再次登录得到相同用户号”必须保持 `PENDING`，不能宣称已经真机验收。

## 8. 错误处理与安全

- 工具请求失败、空结果、无效配置和微信跳转失败分别处理，不用假数据兜底。
- 身份申请使用严格 JSON 解码，拒绝未知字段、空请求、多对象和超出限制的请求体。
- 上传资产必须验证所有权和完成状态，不能引用他人图片。
- 重复提交、重复审核和版本冲突返回可区分的 409 错误。
- 未登录返回 401；非管理员审核返回 403；不存在的申请返回 404。
- API 和日志不得输出 AppSecret、完整 OpenID、访问令牌或证明图片的私密签名参数。
- 用户号使用字符串方式在前端展示，避免 JavaScript 大整数精度问题。

## 9. 验证与验收

### 9.1 自动验证

- 迁移静态测试、幂等测试和独立临时 MySQL 应用测试；
- 申请首次提交、拒绝后重提、待审核重复提交、媒体归属校验；
- 管理员通过、拒绝、自审禁止、版本冲突和事务回滚测试；
- 骑手、商家在未授权和授权后的身份切换及接口权限测试；
- 旧有效骑手和真实配送商家的精确回填测试；
- navigation 服务层过滤无效 `appId`、无效 `path`、占位值和外卖商家目录；
- MiniApp 与 Admin 类型检查、构建和现有业务闭环检查；
- 首页胶囊安全区计算的正常值和兜底值单元测试。

### 9.2 开发者工具与真机验收

- 不同屏幕尺寸下搜索按钮不与微信胶囊重叠；
- “私信｜发现｜工具”切换正常，工具无假数据；
- “我的”上半部分可进入编辑资料，且只触发一次导航；
- 骑手、商家申请、待审核、拒绝重提、通过后切换形成完整闭环；
- 管理员审核后 MiniApp 重新进入或刷新能得到最新身份；
- 配置真实微信凭据后，同一微信账号多次登录保持同一用户号；
- 体验版与真机的 HTTPS 图片、合法域名和外部小程序跳转单独验收。

### 9.3 完成边界

只有自动测试、MiniApp/Admin 构建、开发者工具流程和真实微信真机登录全部通过，才能标记完整验收。缺少 AppSecret、体验版、合法域名或真机时，应明确标记相应项目为 `PENDING`，不能用本地 mock 结果代替。

## 10. 实施顺序

1. 新增迁移和独立身份申请领域模型、仓储、服务与测试；
2. 接入用户和 Admin API，并将现有身份资格判断切换到授权表；
3. 完成 Admin 审核列表和详情；
4. 完成 MiniApp 身份申请页及“我的”入口；
5. 将真实工具作为首页第三页签并修正胶囊安全区；
6. 关闭 mock 登录配置模板中的错误默认倾向，保留机密配置说明；
7. 生成 mock 用户检查报告，执行自动验证；
8. 在用户提供本地真实微信机密配置后进行开发者工具和真机验收。
