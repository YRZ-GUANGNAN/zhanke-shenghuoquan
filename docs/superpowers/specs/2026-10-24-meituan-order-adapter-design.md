# 美团官方订单适配器设计

日期：2026-10-24。基线：`main` / `8dc9af9b06ec5289405010fd02fd381a238a467d`。

状态：依照[共用官方接入设计](2026-10-24-external-platform-connection-design.md)形成的 Provider 子规格。尚未取得本项目美团应用配置、门店授权或生产联调结果。

## 1. 适用范围

本适配器只接美团技术服务合作中心正式授权的外卖订单能力：接收订单变化提示、查询权威订单、归一化为本项目配送所需字段。首期不操作美团接单/拒单、菜品、库存、退款审核、平台配送或结算，不把订单详情当作平台结算凭证。

内部平台枚举继续使用 `meituan`。代码位于独立 Provider 包，通过接口接入 `ExternalIntake`，不得把美团签名逻辑写入通用 `delivery` 领域。

## 2. 官方合同与配置来源

公开美团文档可确认：

- 技术合作中心分配 `developerId` 与签名凭据。
- 需业务授权的接口使用门店授权令牌 `appAuthToken`。
- 多类外卖回调包含 `sign`，部分推送同时包含 `timestamp`、`msgId`、`ePoiId` 等定位/防重字段。
- 不同能力和新旧授权模式可能增加业务标识，例如 `realOpBizCode`；不能按旧样例永久硬编码。

应用获权后必须在账号内锁定以下材料并保存文档版本/获取日期：订单推送清单、订单查询接口、授权流程、签名算法、字符集与参数编码、回调应答、错误码、限频、Token 生命周期和隐私号规则。若账号内合同与公开页不同，以当前获权合同为准并更新固定测试向量后再启用。

部署配置只保存引用：

- `MEITUAN_DEVELOPER_ID`
- `MEITUAN_SIGN_KEY_REF`
- `MEITUAN_API_BASE_URL`
- `MEITUAN_AUTH_BASE_URL`
- `MEITUAN_CONTRACT_VERSION`

`signKey` 实值只在密钥管理服务/受保护环境中存在，不写数据库或 Git。门店级 `appAuthToken` 使用共用 Token 密文表，不使用应用级环境变量共享给全部门店。

## 3. 门店授权与映射

美团授权结果必须最终绑定到：本地商家、平台应用、平台门店稳定 ID、服务商门店映射 ID 和门店级 `appAuthToken`。流程为：

1. 已登录且已通过商家身份审核的用户选择自己的本地商家。
2. 服务端生成短时单次 state，并构造官方授权/门店映射入口。
3. 回调校验 state 后，服务端按当前合同换取或接收门店授权结果。
4. 服务端用官方门店查询能力回查门店标识和授权范围；不能相信浏览器提交的店名/门店号。
5. 用户确认本地商家与美团门店的映射，系统以唯一约束激活绑定。
6. 授权扩展、续期、撤销和重新映射都更新绑定版本并记录审计。

`ePoiId` 如属于服务商自定义门店 ID，由服务端为绑定生成稳定值并持久化，不把本地自增 ID直接暴露为公共映射键。平台门店 ID、`ePoiId` 与本地商家 ID分别保存，禁止混用。

## 4. 请求签名与 API 客户端

实现 `MeituanSigner` 和 `MeituanClient`，只服从获权合同：

- 签名前使用官方规定的参数集合、排序、字符集、空值规则和 URL 编码；不得采用通用“按键排序+MD5”猜测实现。
- 签名输入从即将发送的同一份不可变参数构建，避免签名后参数被中间件修改。
- `signKey`、`appAuthToken`、授权码和完整签名不进入错误、指标或访问日志。
- 使用常量时间比较验证签名；若官方 SDK提供固定向量，纳入仓库测试但不包含真实凭据。
- 响应必须同时校验 HTTP 状态、平台业务码、响应字段、门店归属和订单号。
- HTTP 客户端固定官方主机，限制重定向、响应体和超时；重试只用于合同允许且幂等的查询。

如果美团当前合同要求请求时间戳、nonce、业务编码或签名版本，作为类型化字段加入请求对象；未知或不支持的签名版本使 Provider fail closed。

## 5. 回调验签与应答

美团 handler 保留原始方法、路径、query、Header、Content-Type 和 body。按具体回调类型选择官方验签合同，不在通用 handler 中先转换成 JSON。

处理顺序：

1. 由回调路径中的随机 `bindingKey` 取得有效绑定和 `developerId`/门店映射快照。
2. 限制 query/body 尺寸与字段数量；拒绝重复关键参数和非法编码。
3. 从官方规定的位置读取 `sign`、`timestamp`、`msgId`、`developerId`、`ePoiId`/门店标识。
4. 核对开发者、绑定门店、允许的消息类型和时间窗，再按原始合同验签。
5. 使用平台消息 ID作为第一幂等键；没有 `msgId` 的消息仅按官方稳定字段构造键。
6. 持久化最小回调提示后，返回该消息类型要求的应答。通用 `response.OK` 不可直接复用。

如果官方要求先在时限内应答再异步查询，则成功应答只在持久化提交后返回。数据库不可用、验签失败或无法确定绑定时不得回复业务成功。重复的同内容消息可返回成功；同消息 ID不同摘要进入冲突并告警。

## 6. 订单回查与归一化

收到可信提示后，以门店 `appAuthToken` 调用当前获权的订单查询接口获取权威快照。订单推送与订单查询配合使用，不能只消费一次推送 payload。

归一化规则：

- 完整美团订单 ID映射为 `sourceOrderId`，原字符串保存，不转浮点/短号。
- 美团门店稳定 ID映射为 `sourceShopId`；必须与绑定一致。
- 平台取餐号/日序号仅映射为 `pickupCode`，不承担唯一性。
- 取货点来自已授权门店履约地址；收件人、电话/隐私号、配送地址来自权威订单，并标记可用期限。
- 订单备注做长度、控制字符和 UTF-8 校验；不拼接商品/价格作为备注。
- 平台状态通过显式映射表转换为内部 `created`、`updated`、`cancelled` 或 `unknown`，未知状态不能按新单处理。
- 以平台更新时间/状态版本收敛乱序；只有接收时间而无可比版本时进入人工检查。

若订单查询返回门店不匹配、订单不存在、无权限或关键配送字段缺失，记录分类原因并停止自动发单。隐私号降级通知只更新联系方式可用性，不直接创建重复订单。

## 7. 事件映射与自动发单边界

美团已确认、可履约且未取消的订单才可形成 `created` 候选。后续状态：

- 新订单/确认订单：回查后导入；具体采用哪个官方推送取决于获权业务流程，不能同时把多个阶段都当新单。
- 地址、备注、联系方式变化：作为版本化 `updated`，按共用规则处理。
- 商家/用户取消、退款导致不应配送：作为 `cancelled` 候选，仍须检查本地履约阶段。
- 催单、出餐、隐私号变化、平台配送状态等非创建事件进入专用提示或更新通道，不伪装成新订单。

即使适配器返回可信 `created`，也只授权导入。是否自动扣配送费和开放骑手池由共用 `autoDispatch` 协调器、真实资金和本地状态机决定。

## 8. 错误、刷新与撤销

美团错误映射至少区分：

- `retryable_transport`：超时、临时 5xx、可重试网关故障。
- `rate_limited`：按官方等待信息退避。
- `token_expired`：触发单飞刷新/续期流程（当前合同支持时）。
- `reauthorization_required`：授权撤销、Token 不可刷新、scope 不足。
- `invalid_signature_or_contract`：本地签名或合同版本问题，暂停该 Provider 并告警。
- `shop_mismatch` / `order_conflict`：隔离并人工检查。

授权失效后停止新导入和自动发单，但保留已导入订单履约。重新授权必须确认仍是同一平台门店；换门店按新绑定处理，不能续接旧订单空间。

## 9. 测试与真实验收

自动化测试包括：

- 官方固定签名向量、编码/空值/重复参数、错误 developerId/signKey、时间窗和常量时间比较。
- 错误 `ePoiId`、跨门店 `appAuthToken`、撤销/续期竞争和同消息不同摘要。
- 重复/乱序新单、更新、取消、隐私号变化；未知状态不会自动发单。
- 推送成功而查询超时、查询返回错误门店、字段缺失、限频和 Token 失效。
- Provider 专用应答的 HTTP 状态、body 和超时，确认未泄露凭据/联系人。

真实验收使用官方测试门店或批准的低风险门店，先关闭 `autoImport`/`autoDispatch`，验证授权、推送、查询、撤销和重授权。启用生产自动发单前另行验证资金、退款、通知和暂停开关。没有这些证据时能力接口必须保持未启用。
