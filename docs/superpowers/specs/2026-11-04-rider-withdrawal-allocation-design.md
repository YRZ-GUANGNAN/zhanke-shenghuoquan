# 骑手人工提现收益分配与防重复结款设计

状态：待用户确认的安全补充设计，尚未实施或启用。沿用此前已确认的人工打款产品，不新增自动微信出账。

## 当前问题

`rider_withdrawal_repository.go` 只按钱包总余额扣款，提现申请未绑定具体收益。旧 `PayRiderEarningOffline` 与 `EnsureRiderPayoutQueued` 不了解提现在途/已付金额。因此当前前后台硬门禁必须保留，不能直接将 `withdrawalWritesReady` 改为 true。

历史人工提现设计来自 `d543615`，它不是当前候选祖先。仅复用已批准的产品语义，不合并其旧页面、旧分支或未覆盖风险的开关实现。

## 方案比较

1. **推荐：补收益分配账本并统一互斥，再开放人工提现。** 保留用户选定的业务方式，能追踪每笔钱的真实来源；需要迁移与真实 MySQL 并发验收。
2. 继续关闭提现，仅提供余额/收入/历史记录查询。没有新增资金风险，但不满足本次完整提现目标。
3. 改为自动微信出账。需要另行明确微信转账产品、资质、收款确认、回调、查单与对账，超出当前人工方案，本轮不选用。

## 不改变的业务语义

- 骑手只能提现已完成配送、真实资金来源验证通过且已按北京时间次日00:00结算的收益。
- 申请成功：可用余额扣减一次，申请显示“提现中”。不调用任何外部资金接口。
- 后台确认：管理员已在线下实际转账并填写凭证后，标记已打款，不再次扣余额。
- 后台拒绝：明确原因，原额回充一次，并释放分配。
- 商家钱包、独立保证金、外部订单收益来源、日结时间、订单路由和骑手钱包视觉布局不变；后台仅补资金处理所需的流程动作。

人工转账发生在数据库事务之外，不能只靠“确认/拒绝”状态竞争保护。转账前必须由管理员通过服务端领取处理权，记录操作者、处理版本与唯一操作标识；只有领取者可进入实际打款操作。骑手端仍显示“提现中”，不增加虚构到账状态。

- 未领取的申请可被有权限的管理员拒绝；领取成功与拒绝必须在同一钱包锁及申请版本保护下互斥。
- 已领取、付款结果未知或已线下付但待对账的申请不得拒绝回充、重新领取或二次转账。超时、刷新、服务重启不自动释放处理权或资金占用。
- 操作者明确确认尚未执行转账时，才可通过有原因、有审计的“解除处理”动作回到未领取状态；已转账或结果未知不允许该动作。
- 转账后登记超时只查询原申请及原操作标识，不重转。已线下付但来源核验变化时保存凭证并进入异常对账状态，资金继续占用，不伪装成功或退回余额。

## 分配账本

新增按“提现公开ID、收益公开ID、分配金额（分）”记录的持久化表；每条分配有 in-flight/paid/released 三种状态，并保存骑手、钱包、版本、时间及资金来源核验摘要。

- 单笔提现可跨多条收益；单条收益可部分提现。稳定顺序使用结算时间和唯一ID，不按客户端提交的收益清单认定来源。
- 分配金额必须为正、币种CNY，同一申请与收益唯一。
- 单条收益的在途分配＋已付分配不能超过该收益金额；旧逐单已付和内部队列占用须参与资格判断。
- 一笔 processing 提现的在途分配合计必须等于申请金额；paid 对应已付分配；rejected 对应已释放分配且只有一笔回充流水。
- 无来源的历史余额不能借用未来收益补齐，不伪造已核验资金。
- 若发现历史无分配的 processing/paid 提现或不一致账本，预检拒绝开启；不自动猜测或补造收益。

## 余额与收益口径

服务端新增权威 `withdrawableBalanceCents`：取“账面可用余额减内部队列有效占用”和“当前已结算、来源核验通过的收益剩余可分配金额”的较小值。任一数据缺失、校验失败或占用大于余额时拒绝申请并报告异常，不以客户端计算兜底。

提现申请已经从账面余额扣减，其在途分配只用于收益归属，不再次从账面余额扣减。已付分配永久参与剩余额度计算；拒绝后释放分配并回充一次。收益累计、提现已付、提现在途、可提现分别计算，不能将完全提现的收益改成旧 `paid_offline` 状态或抹去历史收入。

金额全部使用整数分；后端每次加减验证溢出/下溢，API校验数值不超过现有前端安全整数范围；拒绝超过上限的请求或无法安全表达的汇总，不静默截断或转浮点。前端使用新增服务端额度，不继续把 `availableBalance-reserved` 当作可提现额。

## 事务、锁与幂等

以骑手钱包锁序列化该骑手资金动作，多个收益按唯一ID升序加锁；分配选择顺序可以按结算时间，但不能因此改变锁序。跨骑手共用来源记录的锁必须与现有退款及充值资金锁图一致，不能机械采用“钱包后锁来源”并引入反向等待。实施计划须列明实际锁图并经并发测试验证；未完成前不开放。

候选归属可在事务外只读定位，但事务内必须使用当前读重验归属、收益、分配和来源，不能依赖等待钱包锁之前的RR旧快照。所有数据库写入在同一事务中完成；外部人工转账不纳入数据库原子性承诺。

- 创建：身份及参数校验 → 幂等重放核对 → 验证可用余额与队列占用 → 找到完整可分配的真实收益 → 扣款＋申请＋分配＋借记流水＋领域通知原子提交。分配不足整笔拒绝，不允许部分创建。
- 确认：校验处理权、操作者、行版本、凭证和幂等请求 → 复核每项分配的骑手、钱包、收益、订单对应及来源当前状态/证据版本 → 全部转已付＋记录处理审计＋通知原子提交。无分配或金额不守恒拒绝正常确认；已实际付款的异常保留付款证据并转异常对账，禁止回充。
- 拒绝：确认未领取处理且未付款 → 校验操作者、行版本、原因和幂等请求 → 在途分配释放＋原额回充＋调整流水＋通知原子提交。已付/结果未知/处理中的申请不可拒绝，同键异参冲突。
- 旧整单线下结款：只要该收益存在提现在途或已付分配就拒绝；不能把部分已付收益再次按整单支付。
- 内部待打款队列：候选筛选、新建、重新核验与最终处置均检查持久化的在途及已付分配；已在队列的收益不能再被提现分配。队列取消只释放自己的占用，不修改提现分配。
- 资金来源无法确认、数据库结构不完整或通知事务写入失败时，正常资金状态转换全部回滚，保持关闭而非继续扣款。已真实付款的异常凭证须通过独立的审计动作持久化；该动作不回充、不改写成正常支付成功。

人工提现模式启用时，旧后台逐单“登记线下付款”写入口保持关闭，历史只读保留，避免管理员在没有领取处理权的旧页面先实际打款。内部自动建队列开关保持关闭；已有队列占用不自动搬移或释放，须先完成核对及已有审计取消流程。不能同时启用一个会占满全部收益的自动队列，再宣称人工提现可用。存储层互斥仍必须完成，不能仅靠页面隐藏或当前开关保证安全。

## 接口与页面

保持已注册的申请、列表、后台确认和拒绝路由；补充后台受权限保护的领取处理、确认尚未付款后解除处理及异常凭证登记动作。这是资金安全必需的真实接口，不做假入口。现有 `withdrawalEnabled` 能力响应仅在安全实现、迁移和配置均就绪时为 true。

后台删除硬编码禁用时也必须接服务端明确能力；未知、缺字段、请求失败仍禁用。后台仅增加必要的领取/处理状态与审计交互，不重做整体UI。钱包使用服务端可提现额；申请成功只表示资金占用，不宣称微信到账。

新增显式生产配置默认 false。服务启动时验证迁移、账本一致性与依赖；测试通过后另行备份、迁移、部署、受控启用，不能由前端传参解除门禁。

## 必须验收

1. 仅有钱包余额、无核验收益时拒绝；mock、退款、待结算、已线下付来源均拒绝。
2. 部分收益、多收益、跨申请分配守恒；在途和已付不重复分配。
3. 申请重复、同键异参、领取/拒绝竞争、跨管理员处理、确认/拒绝竞争、回充一次、审计凭证不可丢失；转账后登记超时或服务重启不解除占用、不二次转账。
4. 提现与旧逐单支付、队列创建/取消/重新核验、午夜日结同时运行，不重复扣/付、不死锁；覆盖跨骑手共享充值来源与退款竞争。完整资金来源/退款锁图当前尚未验证，不得在实现前宣称通过。
5. HTTP权限、账户隔离、能力关闭、前后台迟到回执及事务通知失败全回滚；来源版本变化、金额溢出、RR旧快照均不能绕过校验；已实际付款的异常不得回充。
6. 真实隔离MySQL并发测试，不以stub测试或人为增加余额代替来源核验。
7. 全量 `npm run verify`、fresh Go test、vet、资金MySQL、通知MySQL、构建和diff检查通过。
8. 生产预检、备份/恢复验证、迁移、默认关闭部署、受控启用逐步记录。真实线下转账仍需管理员本人完成，不纳入自动脚本。

## 本设计之外
