# 骑手自动打款与后台审核备用模式设计

日期：2026-10-24。基线：`main` / `ded4c0455ae07a32991dc0f55f67cb67e3ebaef8`。

状态：用户已明确“保留无人审核自动打款，微信那边过不了再切换后台审核”；本文落实该设计决定，待书面审阅，尚未实施或启用。

## 1. 已确认的产品规则

- 默认审核策略是 `auto`：骑手主动申请提现，系统校验并锁定金额，通过校验后自动提交微信，不要求管理员逐笔点击。
- 保留 `manual`：后台审核通过后再提交同一转账通道。不是将自动打款功能删掉或永久隐藏。
- 自动指“不需要平台人工审核”，不等于用户无需微信授权/确认收款；二者独立配置。
- 不新增每天自动清空钱包、订单送达立即逐笔付款或自动更换收款账号。这些不是本次确认的规则。
- 微信产品权限、业务场景或收款授权不满足时，不伪造开通；后台审核也不能越过微信限制。
- 保持已认可的 UI，仅补钱包余额、提现进度、确认收款和后台结款设置等业务必要区域。

## 2. 现状与依赖

`backend/internal/module/delivery/fee_wallet_model.go`、`fee_wallet_repository.go` 已有收益记录、钱包和流水。`settleDeliveredOrderTx` 在送达事务中记收入，但当前不核对真实资金来源，不能直接用于自动出款。

后台 `POST /admin/delivery/rider-earnings/:id/pay-offline` 仅登记线下已付并扣减账本，不执行真实转账；保留其原含义。`apps/miniapp/src/pages/rider-wallet/index.tsx` 需要接入真实钱包 API，不能只是替换“尚未开放”文字。

必须先满足 [真实支付与来源核验设计](2026-10-24-delivery-payment-integrity-design.md)。通知由 [通知设计](2026-10-24-delivery-notification-design.md) 消费结款事件。

## 3. 审核策略、能力门槛与微信收款模式

三种概念独立保存：

| 概念 | 取值/用途 | 默认或约束 |
|---|---|---|
| `reviewMode` | `auto` / `manual`，决定平台是否逐笔人工审批 | 默认 `auto` |
| `executionState` | `ready` / `blocked` / `paused`，决定是否允许外发资金请求 | 按真实配置、能力核验及应急开关计算，不能假定 ready |
| `receiptMode` | `user_confirm` / `authorized`，决定微信端收款交互 | 无有效免确认授权时使用已具备权限的确认收款模式；不可冒用授权 |

政策记录包含版本、操作者、时间、原因及金额限额。金额上限取平台配置与微信实际限制的较小值；未完成限额配置不开放真实出款。限额校验、账户异常和来源核验属于自动风控，不因 `auto` 而省略。

后台切换审核策略时显示影响：

- 新申请使用新版本。
- `auto -> manual` 对尚未外发的排队单，在同一串行化控制下改为待审核，保留变更前后的策略版本。
- `manual -> auto` 只默认影响新申请，不能静默把旧待审核单全部放行；旧单需显式批准，之后仍走同一幂等提交入口。
- 已提交、待微信确认或结果未知的单，不受审核模式切换重发；继续查询原单。
- worker 外发前再次核对策略版本、暂停标记及租约。与切换并发时以事务认领/提交标记为边界，已进入外发阶段的记录按在途单处理。

## 4. 微信侧不支持时的处理

1. 首次开通或能力核验发现微信不允许当前模式：保留 `auto` 功能，阻止真实外发，显示原因，允许管理员切换 `manual`。
2. 明确的权限撤销/产品能力拒绝触发通道暂停与后台告警；不将普通网络故障误判为需人工审核。
3. 未外发的申请可以转待审核。对已经尝试提交的申请，先确认微信未受理或已达失败/撤销终态，再允许新的受控尝试。
4. 切换 `manual` 不恢复不存在的微信产品权限；审核后仍阻止不满足权限的转账。若选择合法的线下结款，必须确有外部付款凭证后才能登记，不能把后台“批准”当作已到账。
5. 账户余额不足、收款人需确认、微信风控拒绝等分别显示与处置；不自动换 API、收款人、商户号或业务场景绕过限制。
6. `unknown` 不释放资金、不换单、不登记线下已付；先查原单和对账。

## 5. 提现与转账状态机

以下为新增的内部状态定义，不宣称是当前代码或微信原始状态。提现申请与外部转账尝试分开建模。

| 提现状态 | 含义 | 资金占用/下一步 |
|---|---|---|
| `pending_review` | 人工模式待批准，或已安全转人工处理 | 保留锁款；可批准、驳回或在无在途尝试时取消 |
| `queued` | 自动校验通过或已人工批准 | 保留锁款；持久化转账尝试后外发 |
| `submitting` | 已标记外发，不能保证微信尚未接收 | 保留锁款；提交/查询原业务号 |
| `processing` | 微信受理但未达终态 | 保留锁款；异步通知加主动查单 |
| `awaiting_receipt` | 等待骑手在微信确认收款 | 保留锁款；展示确认入口，不重新创建提现 |
| `unknown` | 超时、断网、不可识别结果 | 保留锁款；查单、告警及对账 |
| `succeeded` | 可信微信结果确认成功 | 原子扣减账本、消耗占用、生成流水和事件，且仅一次 |
| `failed` / `cancelled` / `rejected` | 明确失败/撤销，或未外发前终止 | 无其他在途尝试时原子释放占用，且仅一次 |

每笔转账尝试有不可变的 `out_bill_no`、收款身份/模式/金额/场景快照、请求摘要及来源提现 ID。HTTP 成功、受理和收款页关闭都不是到账证明。只有原尝试已确认结束，才允许在原提现业务下创建受控的新尝试；不得同时存在两笔可能成功的转账。

重新请求同一幂等键返回原申请；同键但金额、身份或参数不同返回冲突。明确失败且已释放后重新提现属于新申请，不能复用已结束的微信业务号。生产测试及后台操作都走同一状态机。

“超时未收款”由查单确认终态后才能释放，不根据本地时间擅自认定撤销完成。无法在线查清的旧单转账单/资金账单对账，绝不自动回滚成可提现。

## 6. 资金守恒、收入分配与历史数据

- 保留已有钱包总账，新增提现占用、提现收益分配与外部转账尝试记录；不改旧 `RiderPayoutRecord` 的“线下实付”含义。
- `withdrawableBalanceCents` 由已核实、无争议、未支付的收益减去在途占用得出；不能直接用既有 `AvailableBalanceCents` 当作真实可提现金额。
- 首期支持骑手选择整数分金额，不得超出可提现余额。按照收益创建时间与公开 ID 的稳定顺序分配，可部分占用某条收益。
- 对任一收益：已实付分配 + 在途占用不得超过真实可付金额；一份收益不能既在线上占用又被线下全额支付。
- 锁款仅建立占用，不预先写“已付款”的出账流水；成功时扣账本并消耗占用，失败时只释放占用，不凭空增加收益。
- 旧 `pay-offline` 是整笔收益登记，因此仅当该收益没有任何在线占用或已付分配时可用；部分线上已付后禁止再走旧整笔登记接口。
- 新增在线已付的状态/展示时保留 `pending`、`settled`、`paid_offline` 历史值语义；部分付款通过分配金额表达，不能提前把整条收益标记为全额结清。
- 锁顺序统一为钱包、按稳定顺序的收益/来源、提现及分配；现有线下路径需同步调整锁序。所有路径都用数据库唯一约束、行锁/CAS，不能只靠前端按钮禁用。
- 收入被退款/争议冻结后阻止新提现；已在微信处理的单先核实，产生差异进入对账异常，不自动生成负余额或强制追回。
- 历史来源未知和 mock 收益仍可查，但不可自动提现；迁移不直接抹去旧收入或伪装真实付款。

## 7. 接口与界面职责

沿用仓库的 rider/admin 路由分组；以下是拟新增操作，不改变订单接口：

- 骑手：查询自己的钱包汇总、收益明细、分页账单和提现记录；创建提现；查询单笔结果；在允许时取消；获取本人微信确认收款参数。
- 后台：查询提现/在途/异常记录，查看脱敏原单号和对账结果；切换审核策略/暂停外发；审批/驳回待审核单；触发查原单与受控重试。
- 自动与人工审核都记录规则结果、策略版本和审计事件，人工批准不能绕过资金来源与支付能力检查。
- 后端从会话和可信绑定读取收款身份，不能接受客户端随意传入他人的 `openid`。收款身份变更不能影响已创建的尝试。
- 已认证但休息中的骑手可查账和申请提现；接单状态不等于资金冻结。被冻结或身份异常账户保留查询/申诉路径，不能静默删除余额。
- 后台批准、设置和重试使用既有管理权限与防跨站请求保护；记录操作者、原因和版本，不给普通骑手暴露他人钱包。
- 钱包显示可提现、处理中、待核验及已结款；今日收入/单量保留原定义，不能与可提现混为一谈。

建议职责分离：`delivery` 内独立提现领域文件；微信转账独立适配器；rider/admin handler 只负责鉴权和 DTO；worker 只负责任务认领与协调。不要把全部逻辑堆入现有支付 handler。

## 8. 公众号通知与异常处理

产生提现已受理、转人工待审核、审核拒绝、待确认收款、转账成功、明确失败及通道停用事件。用户通知不得把 `queued`/`processing` 写成“已到账”。后台通道异常通知与骑手业务通知分开；未送达通知不回滚付款。

## 9. 验收

必须覆盖：

1. 默认 `auto` 无人工操作即可从合法申请进入 Provider 提交；`manual` 在批准前绝不外发。
2. 策略切换与 worker 抢占竞争；旧待审核单不被静默批量放行；在途单不重发。
3. 商户权限不足、配置缺失、收款授权失效、余额不足、金额超限分别处理；`manual` 不绕过权限。
4. 双击、多端、并发提现和线下结款竞争；同一收益资金不超额占用、不双付。
5. 回调早于提交响应、重复/乱序回调、超时后实际成功、worker 崩溃后恢复；只记一次扣款。
6. 待确认收款、用户放弃页面、本地超时与微信实际撤销不同步，不误释放。
7. mock/旧未知资金、争议款不得进入自动转账；历史余额展示和今日统计回归。
8. 用户越权、收款身份篡改、签名/金额/主体不匹配拒绝并记录审计。
9. 使用独立 MySQL 进行锁与唯一性验收，使用隔离 HTTP server 验证两种收款适配流程。真实验收另列，未执行不得报告自动打款已可用。

继承支付设计的 Go、typecheck、构建和契约验收，新增状态机/Provider/并发测试由后续实施计划列出精确命令。测试不得访问生产转账接口。本文提交不启用真实支付开关、不部署、不执行迁移或真实打款。
