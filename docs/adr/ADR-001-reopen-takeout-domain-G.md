- **版本**：v1.1（v1.0 草案基础上：支付/资金段收口 + 状态改为已接受）
- **日期**：2026-06-22
- **决策者**：owner
- **相关文件**：`ARCHITECTURE.md`、`README.md`、`DEVELOPMENT.md`、`docs/DEVELOPMENT_DISCIPLINE.md`

## 背景

项目此前按"半成品系统收敛重构"固定为 A–F 六业务域，并明确删除旧原型的订单与支付能力：

- `ARCHITECTURE.md` 第 43 行：`sold` 为终态；旧的订单模型已删除，当前系统不承担支付或自建订单能力。
- `ARCHITECTURE.md` 第 58 行：已删除订单表 / 接口……
- `ARCHITECTURE.md` 第 60 行：不恢复未归类的……支付……功能。
- `DEVELOPMENT.md`：无法归属 A–F 的需求不进入当前系统。
- 真实库经 P0-4 核查无任何 order / merchant / dish / payment / rider 表。

owner 决定重新引入"校园外卖"。外卖的本质是下单 + 支付 + 配送，无法归入 A–F 任何一域——它恰好需要上述被删除并禁止恢复的两样（订单、支付）。因此这是对一个已冻结架构决策的有意反转，以本决策记录显式登记。

## 决策

1. 正式引入第七业务域 **G 外卖**，与 A–F 同级，遵循 `DEVELOPMENT_DISCIPLINE.md`。
2. **在且仅在域 G 范围内**反转 `ARCHITECTURE.md` 第 43、58、60 行关于"订单 / 支付已删除且不恢复"的条款；A–F 与媒体子系统的相应约束不变。
3. 域 G 登记：后端 `internal/module/takeout`；入口 `services/g-takeout.ts`；路由根 `/takeout`（`/api/v1/takeout`）；自有数据由 G 各模块迁移定义（迁移自 `016` 起，每条配 `rollback/`）。
4. 依赖规则（复用而非重建）：身份复用 A（买家/商家/骑手均为 `user`+角色，仅存 `user_id` 逻辑引用、**禁止跨域外键**）；图片走媒体子系统（`media_asset_references` 引用、展示经 MediaGateway，仅 final+approved）；商家/菜品审核提交 F 统一审核流；会话经 E `ConversationGateway`；G 自有仓储只访问 G 自有表。
5. 实现范式与媒体一致：`expected_status + row_version` 的 CAS；副作用走 Outbox → Consumer + Inbox 去重；fail-closed；真实 MySQL 8.4 验收；残留 = 0。

## 支付与资金范围（第一版 / 本 ADR 锁定）

收款主体为 **个体工商户**，使用其**微信支付商户号（mch_id）**。范围严格如下：

### 真实资金（仅"买家 → 平台"单向收款）
- 买家下单经微信支付（个体户商户号）收款；金额服务端重算，不信前端。
- 退款：商家拒单 / 取消 / 无人接单 → 原路退回。
- 收款与回调结构对齐媒体 Ticket + Completion + Outbox：幂等、防重复、fail-closed。

### 骑手报酬 = 展示型钱包（方案 A，不出账、不存余额）
- **余额是算出来的，不是存起来的。** 系统**不设** `balance` 字段；骑手"待结算"金额始终等于其名下 `结算状态 = 待结算` 的应结明细之和。
- **应结明细**（`rider_earning_record`）：每张订单进入完成态时落一条，字段含订单号、骑手、**骑手单价快照**、**平台抽点快照**、周期、`结算状态`（待结算 / 已结算）。此明细即第二版接入 ledger 的数据接口。
- **提现 = 申请，不是出账**（`withdraw_request`）：骑手发起 → `待处理`；owner 在后台查看、**线下微信转账**、点"已打款" → `已打款`，并将对应应结明细标记 `已结算`。**系统全程不转出任何资金。**
- 骑手小程序钱包页为**只读**：待结算（实时算）、已结算、提现申请入口。

### 费率可配（后台自主设置）
- 后台可设"当前费率"：**骑手单价**、**平台抽点**。
- 改费率**只影响其后产生的订单**；每张订单在完成那一刻把当时费率**快照**进其应结明细，旧单永不变。

### 第一版明确不建（留待第二版，且能直接读应结明细接上）
- 真 `balance` / `frozen_balance` 余额字段；
- ledger 资金账本；
- 自动出账（平台 → 骑手的系统转账）；
- 收益自动入账逻辑。

> 升级路径：第二版接入真钱包时，ledger 的"入账"读取 `待结算` 应结明细、"提现"由 ledger 驱动出账；底层"每单该给谁多少"在第一版已备齐，无需回填或改订单逻辑。

## 模块拆分（各自专项授权、PASS 后 commit + tag 冻结）

| 模块 | 范围 | 碰真钱 |
| --- | --- | --- |
| G-① Merchant | 商家实体、入驻、营业状态机（owner 复用 A；logo 引用 media） | 否 |
| G-② Catalog | dish / category、上下架状态机（菜品图引用 media，展示走 MediaGateway） | 否 |
| G-③ Order | orders / order_item、下单、订单状态机（CAS）、金额服务端重算、下单快照、**完成时落应结明细（费率快照）** | 否 |
| G-④ Payment | 微信支付收款 + 退款（个体户商户号），对齐 Ticket+Completion+Outbox；幂等、fail-closed | **是（仅收款/退款）** |
| G-⑤ Rider | rider 实体、抢单（CAS，无派单算法）、履约状态机（独立于订单主状态机，仅经事件影响订单终态） | 否 |
| G-⑥ Admin | 商家/菜品/订单管理 + 接入 F 审核流 + **费率设置 + 结算报表 + 提现申请处理（标记已打款/已结算）** | 否（人工转） |
| G-⑦ Miniapp | 小程序页面 + 业务接线、`Taro.requestPayment`、上传走既有 media 链路、**只读钱包/提现申请** | 否 |

购物车置于前端 Zustand，不单列后端模块。钱包/提现为 G-⑥（后台处理）+ G-⑦（骑手端只读展示）的轻量部分，**不单列资金域**。

## 影响与风险

### 范围与纪律
- A–F 收敛被有意放宽：系统重新承担收款。后续不得以"既然 G 能扩、别处也能扩"类推；其它域扩张仍需新 ADR。
- 媒体子系统（Module ②–⑩）与 A–F 契约不受影响，保持冻结。

### 生产库形状约束（来自 P0-4）
- 当前生产库为 **形状 Y**，与迁移 001–015（形状 X）相差 **68 项**跨域漂移（已登记，未对齐）。
- **在"68 项对齐"专项被接受前，禁止仅用迁移重建生产库。** G 各模块迁移只新建 takeout 自有表、对 A–F 仅逻辑引用零外键，不依赖 A–F 表的列形状，从而不受该 68 项漂移影响。

### 资金与对账（owner 承担）
- 第一版"骑手报酬"由 owner 人工微信转账并在后台标记；系统不保证"送单数 = 已付金额"，该一致性由 owner + 后台报表保证。报表须按订单明细可追溯，以备纠纷。
- 个体户须办妥微信支付商户号 + API 密钥/证书（仅营业执照不足）。

## 后续

1. 据本 ADR 修订 `ARCHITECTURE.md`、`README.md`、`DEVELOPMENT.md`（登记域 G、对支付/订单禁止项加例外指针 → 本 ADR）。
2. 按 G-①…G-⑦ 逐条专项授权；G-④ 须在商户号办妥后启动，其余不阻塞。
3. 本 ADR 不定义任何表结构；迁移自 `016` 起。
